## L1 — AI Agent 是什么:从 Chatbot 到 Agent

### 一、基本信息
- **课时编号**:L1
- **课时时长**:90 分钟
- **课型**:理论 + 讨论(无代码)
- **前置知识**:了解 ChatGPT / Claude 等 LLM 应用的基本使用
- **配套资料**:`../../docs/agent-development-guide.md` 第 0 节

### 二、教学目标
**知识目标**
- 准确说出 Chatbot、Workflow、Agent 三者的边界与判断依据。
- 列出并解释 Agent 的 4 个核心组件(LLM / Loop / Memory / Tools)。
- 复述"自主性谱系"5 个层级,并能在谱系上为给定系统定位。

**能力目标**
- 能用一句话清晰定义"AI Agent"。
- 能针对一个业务需求,判断"该用 Chatbot、Workflow 还是 Agent",并写出 2 条理由。

**素养目标**
- 建立"先想清楚再写代码"的产品思维:在动手前先回答"目标 / 输入 / 输出 / 约束"。

### 三、教学重点与难点
- **重点**:Agent 的 4 个核心组件;ReAct 循环的直觉理解。
- **难点**:让学员真正理解"自主性"——Agent 不是更强的 Chatbot,而是会**改变世界**(产生副作用)的程序。

### 四、教学准备

**【教学素材】**
- **3 个真实 Agent 案例**(讲师提前熟悉,现场演示或截图讲解,每个 2 分钟内):
  1. **Cursor Agent 模式**:准备一段 15 行代码有 bug,让 Cursor 自己 grep → 定位 → 修 → 验证 → 说明。**演示重点**:每步 Cursor "决定下一步做什么"是 LLM 而非人。
  2. **Claude Code / Codex CLI 命令执行**:让它跑一个"扫描当前目录、找出所有 `TODO` 注释、生成 markdown 报告"的任务,展示"读文件→分析→写文件"的多步循环。
  3. **DevOps 巡检 Agent 反例**(可用讲师自造 mock):固定 cron 每 5 分钟拉一次监控 → 有阈值告警时套模板发 Slack ——**这是 Workflow 不是 Agent**,用来做对照。
- **对比卡片 3 张**(A5 打印或投影):
  - 案例 A:"客服自动回'营业时间'" → Chatbot
  - 案例 B:"定时拉 GitHub PR 评论套模板生成日报" → Workflow
  - 案例 C:"用户上传简历→AI 审→改写→PDF→发邮件"(取决于步骤谁决定) → 视情况

**【教学材料】**
- **一句话金句板书**:"Agent = 会循环 + 会用工具 + 会留下副作用 的 LLM 程序"——课末合影板书用。
- **4 组件比喻表**:LLM=大脑 / Loop=心跳 / Memory=笔记本 / Tools=双手(下文六节板书已有,课前熟读)。
- **自主性谱系图**(Prompt → Prompt+Tools → Workflow → Agent → Multi-Agent),提前画好 mermaid 或手绘扫描件备投影。

**【学员课前】**
- **无需**开发环境。带纸笔即可,课上有 3 张讨论卡片和 5 题测查需要写答案。
- **可选预习**(15 分钟):Anthropic 官网《Building Effective Agents》一文,只看 "Agent vs Workflow" 一节。

**【备用方案】**
- 若 Cursor / Claude Code 无法现场联网 → 改放**预录 2 分钟 GIF/视频**演示同一效果。
- 若讨论环节冷场 → 备一个"催化提问":"你们组里最耗时的重复流程是什么?其中'看到 A 结果决定做 B 还是 C'的分支占多少?" ——分支占比高就是 Agent 候选。

### 五、教学过程

#### 1. 导入(8 min)

**【互动开场】** 让 3~4 位学员举手分享:"过去一周你用 ChatGPT 做过哪些事?"

讲师把学员说的事**分两栏**写在白板上:
- 左栏:"它只是回答了我"(查信息、改文案、解释概念)
- 右栏:"它真的替我做了某件事"(改了文件、发了消息、调了 API)

> 【讲师讲稿】"大家发现没有?左栏的事情,本质上 ChatGPT 是一个**会聊天的搜索引擎**——它把答案告诉你,真正动手做事的还是你。右栏的事情就不同了,系统要真的去**碰外部世界**:打开文件、调用 API、发邮件、转账。今天这节课要讲的 AI Agent,核心就是右栏这种'会动手'的程序。我们要先把'Chatbot 和 Agent 到底差在哪'这个问题彻底说清楚,因为这是后面所有课的基础。"

#### 2. 概念建模:Chatbot vs Agent(20 min)

在白板画出对比图:
```
Chatbot:  用户 ── 文字 ──▶ LLM ── 文字 ──▶ 用户
                              (一问一答,无副作用)


Agent 主循环(每一轮 = LLM 做一次二选一):

              ┌────────────────────────────────┐
              │ ①  从记忆读取 messages         │◀───────────┐
              └────────────────┬───────────────┘             │
                               ▼                             │
              ┌────────────────────────────────┐             │
用户 ─目标 ─▶│ ②  LLM(大脑)决策:            │             │
              │     msg.tool_calls?            │             │
              └────┬──────────────────────┬────┘             │
                   │                      │                  │
   分支 A: is None │                      │ 分支 B:非空       │
   (final answer)  │                      │ (tool_calls)     │
                   │                      ▼                  │
                   │              ┌───────────────┐          │
                   │              │ ③  执行工具   │          │
                   │              │    (Tools)    │          │
                   │              └───────┬───────┘          │
                   │                      │                  │
                   │                      │ 返回 obs         │
                   │                      ▼                  │
                   │              ┌───────────────┐          │
                   │              │ ④  写回记忆   │──────────┘
                   │              │  append obs   │  (obs 回到 ①,进入下一轮)
                   │              └───────────────┘
                   │
                   ▼
              ┌──────────┐
              │   用户   │ ◀── 最终答案(str)  ← Agent → 用户 唯一出口
              │  (退出)  │
              └──────────┘


──────────────── 循环之外:外部依赖(不属于 4 步主循环) ────────────────

       ┌──────────────────────────────────────────┐
       │  外部世界:HTTP API / DB / 文件系统 /     │
       │           MCP server / 内部 RPC / ...    │
       └──────────────────────────────────────────┘
                         ▲
                         │  ③ 调用 fn(args)(同步等结果)
                         │  返回值 → 立刻转成 obs → 走 ④ 入循环
                         │


图的准确性约束(务必对齐):
  ✅ ②(final answer) → 用户   :LLM 主动结束时,把 content 字符串交给用户
  ✅ ②(tool_calls)   → ③ → ④ → ①:工具流永远经"记忆 → LLM"回到决策,不外泄
  ✅ ③ ⇄ 外部世界             :同步"调用/等返回",是 ③ 的实现细节
  ❌ ③ → 用户                 :**没有** "执行工具直接给用户答案" 这条流
  ❌ ④ → 用户                 :**没有** "写完记忆直接给用户答案" 这条流
  ❌ 外部世界 → 循环任意节点    :**没有** "外部世界主动推给 Agent" 这条流(除 ③ 拉取)
```

> 【讲师讲稿】"这张图两条路径,请大家严格区分,后面 4 节课都要反复回到它。"

> "**第一条:循环路径(右侧向下再折回上方)**——LLM 决定调工具 → 工具执行 → 产生观察(obs)→ **把 obs 写回记忆** → **回到 ① 让 LLM 读全新上下文重新决策**。注意关键:**记忆写完之后是回 LLM,不是回用户**。记忆只是这个循环的'笔记本',每一步把新内容写下来、下一步给 LLM 读,它本身**不是终点、不是决策点**——**决策点永远只有 LLM,终点永远只有'用户拿到最终答案'**。"

> "**第二条:退出路径(左侧向下)**——LLM 在每一轮决策时,都可能直接给出'最终答案'(即 `msg.tool_calls is None` 的情况)。一旦给出最终答案,**这个答案作为字符串直接返回给用户**,循环立刻终止。也就是说:**Agent 不是'跑完 N 步才出来',而是 LLM 自己说我够了的那一刻,把答案送到用户手里就出来**——这跟传统 for 循环跑固定次数完全不同。"

> "两条路径合起来看,Agent 的每一轮就是 LLM 在做一道二选一:**继续调工具(走右侧循环 → 记忆 → 回 LLM),还是给最终答案(走左侧退出 → 送给用户)?** 后面 L4 我们写伪代码时,就是把这两条路径落成 `if msg.tool_calls: 执行工具+写回记忆+continue else: return final_answer_to_user` 的两行代码。"

> "**常见误解 4 个,一次纠正:**"
> "  ① '循环停在工具' —— 错。工具只负责产生 obs,obs 必须回 LLM,否则模型看不到自己动作的结果。"
> "  ② '循环停在记忆' —— 错。记忆是储存介质,不是决策者;写完记忆下一步必然是 LLM 再决策。"
> "  ③ '记忆更新完就把结果给用户' —— 错。**只有 LLM 主动说 final answer 时,答案才走左侧退出到用户**;记忆写完永远回 LLM。"
> "  ④ '外部世界是循环的第 5 个节点' —— 错。**外部世界不在主循环里**,它是 ③ 执行工具时按需调用的下游依赖(HTTP API / DB / MCP…);③ 拿回返回值后立刻转成 obs 继续走 ④,外部世界从不主动推消息进循环。"

**【讲师讲稿】**

> "我们先看 Chatbot。Chatbot 的数据流非常简单:用户发一句话,LLM 生成一段回复,完事。它的特点是**无状态**(每次对话相对独立)、**无副作用**(不会改你的文件、不会发邮件)、**单回合**(一次问一次答)。最典型的就是普通的 ChatGPT 网页。"

> "Agent 完全不一样。我给 Agent 的不是'一句话',而是一个**目标**——比如'我们支付接口今天早上延迟突然升高,帮我查一下大概是什么原因'。Agent 收到目标后,**步骤不是我事先想好告诉它的**:它可能先去看监控曲线,发现是某台机器异常,再去拉这台机器的日志;日志里看到一段错误堆栈,又去 git 查最近相关的提交……每一步看到什么,**直接影响下一步去查什么**——这种'走一步看一步'的决策只能 LLM 在运行时做,你没法提前写死。每一步的结果也会被记下来,作为后续决策依据。"

> "**注意这里的关键不是用了几个工具,而是'步骤由谁决定'**——是 LLM 看到上一步结果后临场决定的,这才叫 Agent。一会儿案例 2 我们会看一个反例:同样涉及 GitHub 和 Slack,但流程是事先写死的,那个就不是 Agent。"

> "所以 Agent 比 Chatbot 多了三样东西:**循环**(Loop)、**工具**(Tools)、**记忆**(Memory),再加上原本就有的 LLM 大脑,合起来就是今天的核心公式——**Agent = LLM + Loop + Memory + Tools**。"

**逐一展开 4 个组件**,每个组件用一个生活化比喻 + 一句话技术定义:

| 组件 | 一句话比喻 | 技术定义 | 讲师讲稿要点 |
|---|---|---|---|
| **LLM** | 大脑 | 自然语言推理与决策引擎 | "Agent 的所有'判断该做什么'都来自 LLM。没有 LLM 就不叫 Agent,只叫脚本。" |
| **Loop** | 心跳 | "决策—行动—观察"反复执行的主循环 | "Loop 是 Agent 区别于一次性函数调用的本质。模型每一步只决定下一步做什么,而不是一次输出全部答案。" |
| **Memory** | 笔记本 | 跨步骤、跨会话保留状态 | "短期记忆 = 当前 messages 列表;长期记忆 = 向量库 / 数据库。没有 Memory,Agent 永远只活在'当下'。" |
| **Tools** | 双手 | 让 LLM 能够调用的外部能力 | "工具是 Agent 与世界的接口。GitHub API、本地文件、SQL 查询、发邮件……都是工具。" |

> 【讲师金句】"记住这句话——**Agent 是会循环、会用工具、会留下副作用的 LLM 程序。** 这 19 个字就是 Agent 的本质。"

**提问检查理解**:
- "如果我写一个 Python 脚本,定时调用 ChatGPT 改写一句话再保存到文件,它是 Agent 吗?"
  - 期望答案:**不是**。它有副作用但没有"模型决定下一步"——流程是写死的,属于 Workflow。
- "Cursor 里的对话回答算 Agent 吗?它能改我代码。"
  - 期望答案:**算 Agent**。因为它会决定调用哪个工具(edit_file、grep、run_terminal)、调几次、要不要再调,这是循环决策。

#### 3. 案例研讨:Chatbot / Workflow / Agent(20 min)

**【活动设计】** 分发 3 张案例卡片,学员两人一组,3 分钟讨论一张,讲师巡视并最后统一点评。

**案例 1**:客服自动回复"营业时间是几点"。
- **答案**:Chatbot。单轮问答、无外部副作用、流程固定。
- 讲师追问:"如果要回答'我的订单到哪了',就升级了——为什么?" → 需要查订单 API,有外部依赖,得变 Agent。

**案例 2**:每天早上 9 点**定时**从 GitHub 拉昨日 PR 评论,**套固定模板**生成日报发到 Slack(顺序写死:拉 → 套模板 → 发)。
- **答案**:Workflow,不是 Agent。
- 讲师追问:"它有副作用啊,怎么不是 Agent?" → 关键在"流程是写死的",模型只是模板里"生成一段摘要"的一个环节,**没有在运行时决定下一步**。
- 与第 2 节呼应:**对比刚才"查支付接口为什么变慢"的例子**——那个例子里步骤完全由模型边看结果边决定,这个例子里步骤是程序员事先写好的。两者表面都涉及外部 API + LLM,**关键区别就是"步骤谁决定"**。
- 进阶:"如果把这个例子改成'让模型先判断昨天值得汇报的内容是哪几类、要不要单独 @ 给某个 owner、要不要补充一段风险提示',那就升级成 Agent 了——因为模型重新拿回了"运行时决定下一步"的权力。"

**案例 3**:用户上传简历 → AI 自动审核 → 生成改写建议 → 生成 PDF → 发邮件给用户。
- **答案**:**取决于实现**。如果流程写死(`扫描 → 改写 → PDF → 发邮件`),是 Workflow;如果让模型决定"这份简历哪些段落需要重写、要不要补充 cover letter",就是 Agent。

> 【讲师讲稿】"案例 3 是想告诉大家:**Agent 和 Workflow 不是看做什么,而是看谁决定流程**。流程是人写死的就是 Workflow,流程是 LLM 在运行时动态决定的就是 Agent。这一点请大家牢牢记住,后面 L6 选型课会再回到这个判断。"

#### 4. 自主性谱系(15 min)

白板画出谱系:
```
低 ──────────────────────────────── 自主性 ─────────────────────────────▶ 高
Prompt → Prompt+Tools → Workflow → ReAct Agent → Multi-Agent System
(纯回答) (能调工具) (固定流程) (LLM 决定流程)  (多 Agent 协作)
```

**【讲师讲稿】**

> "我们今天讲的'Agent'其实只是这个谱系上一个区间。要注意,**自主性不是越高越好**——自主性越高,意味着越不可控、越费钱、越难调试。所以选型时要按需取最低的合适层级。"

> "举几个例子:你只是想要 GPT 帮你润色文案,Prompt 就够了;你想让它'查完天气再润色一段播报词',Prompt+Tools 够了;你想要每天定时跑、流程固定,Workflow 够了;你想让它'拿到不确定的输入后自己分情况处理',这才需要 Agent;你想要'分析师、写手、校对'三个角色互相配合,才考虑 Multi-Agent。"

> "我经常看到团队上来就说'我们要做一个 Multi-Agent 系统',这通常是过度设计。**先用更低层级把问题解决,解决不了再升级**——这是我希望大家从第一节课就建立的工程原则。"

**埋伏笔**:"L6 我们会专门讲选型决策树,L25 会专门讲 Multi-Agent 的代价。"

#### 6. 布置作业(2 min)
- 写一篇 200 字短文:**"我工作中最适合改造成 Agent 的 1 个流程"**,要求点明:
  1) 当前流程是什么;
  2) 为什么是 Agent 不是 Workflow;
  3) 需要哪些工具。
- 下节课课前邀请 2 位上台展示 90 秒。

**参考答案(范文示例,供讲师讲评用)**:

> 我团队每天有 6~10 个 P1 客户工单进入。**当前流程**:客服收到工单 → 手动看错误日志 → grep 找根因 → 查 wiki/Confluence 找类似案例 → 召集 owner → 给客户写复盘。耗时 30~120 分钟,70% 时间花在"找信息"。
>
> 改造成 **Agent 而非 Workflow**,因为:① 不同工单的"找根因"路径不固定,有时先看 trace 再查日志,有时反过来,**步骤顺序由 LLM 当下推断**而不是模板写死;② 中间会动态决定要不要召集 owner、要不要重启服务,这需要**条件分支**;③ 输出是"自然语言根因解释",非纯结构化。
>
> **需要的工具**:`grep_log(time_range, keyword)`、`query_metrics(service)`、`search_wiki(text)`、`get_recent_deploys(service)`、`page_owner(service, reason)`、`post_to_slack(channel, msg)`。前 4 个只读安全,后 2 个有副作用,建议加 HITL 审批(M6 会讲)。

**评分维度**(每项 2 分,共 8 分):
1. 流程描述具体清晰(非"我用 AI 写代码"这种含糊);
2. Agent vs Workflow 的判断有理由(挂上"动态决策"或"条件分支");
3. 工具列表 ≥3 个且粒度合理(不是"AI 助手"这种黑盒);
4. 指出哪些工具需要 HITL(体现安全意识)。

---

#### 2. Token:LLM 的计量单位(25 min,含 BPE 详解 5 min)

> 【讲师讲稿】"先讲 token。Token 是 LLM **计算和计费的最小单位**。你输入的'你好,世界'这五个字符,在模型眼里不是 5 个字符,而是被切成 N 个 token。"

> "为什么要 token 化?因为模型的输入层是一个**有限的词表**(vocabulary),通常几万个 token。原始文本要先映射到词表里的 ID,模型才能处理。常见的 token 化算法叫 BPE(Byte-Pair Encoding),它会把高频的字节对合并成一个 token。"

---

##### 形象解释 BPE:从"背单词"到"压缩词表"(5 min)

讲师在白板上写一个类比:

> 【讲师讲稿】"BPE 听起来高大上,其实就是**模仿人类背单词的过程**——"

> "**第 0 天**:你刚学英语,只认 26 个字母。你看 `the` 这个词,得**一个字母一个字母拼**:t-h-e,**3 个动作**才认完。"

> "**第 N 天**:你已经无数次见过 `th` 这个组合(在 the / this / that / they / there 里都出现),大脑就**把 'th' 自动当一个东西**了。"

> "**第 N+1 天**:你又发现 `the` 整个词出现得超频繁,干脆**把 'the' 整体当一个东西**记下来。从此以后看到 the,**一个动作就识别**,不用再拼。"

> "**BPE 就是机器版的这个过程**:扫描海量语料,**反复把'最常一起出现的相邻片段'合并成一个新 token**,直到词表大小达到设定上限(比如 OpenAI 老编码 `cl100k_base` 是约 10 万个 token,新编码 `o200k_base` 是约 20 万个)。"

---

**手算 demo**:假设语料就这 3 个词,每词出现的频次写在前面:

```
5  l o w
2  l o w e r
6  n e w e r
```

初始词表是字符级:`{l, o, w, e, r, n}`。一轮一轮合并:

```
Round 1:扫所有相邻 pair 的出现频次
  (l,o):5+2=7    (o,w):5+2=7    (w,e):2+6=8    (e,r):2+6=8    (n,e):6    ...
  最高 8(并列),挑 (e,r) 合并  →  新 token "er",加进词表

Round 2:语料里 "er" 现在是一个整体
  (l,o):7    (o,w):7    (w,er):2    (n,e):6    (e,w):6    ...
  最高 7(并列),挑 (l,o) 合并  →  新 token "lo"

Round 3:(lo,w) = 7,合并  →  新 token "low"

Round 4:(n,e) = 6,合并  →  新 token "ne"

...一直跑到达到词表上限就停。
```

跑完后,常见词整个就是 1 个 token:`low` 是 1 token(原本 3 字符)、`er` 是 1 token、`new` 可能是 1 token……**稀有词**仍然按更小颗粒切。

> 【讲师讲稿】"看见效率提升了吗?**频繁出现的'模式'被压缩成 1 个 token,稀有模式按字符细切**。这是 BPE 在'词表大小'和'切分粒度'之间找到的平衡——既不像'按字'那么细(token 数太多),也不像'按词'那么粗(词表无穷大,生僻词查不到)。"

---

##### 为什么 GPT-4o / 4.1 中文突然便宜了一半

> 【讲师讲稿】"理解了 BPE,刚才那个'新旧 encoding 差一倍'的现象就解释得通了。"

> "**关键在训练语料的语种分布**——`cl100k_base`(GPT-3.5 / 原版 GPT-4)是 2022 年训练的,中文语料占比小,所以 BPE 跑下来,'你好'、'世界'这种高频中文词组**没机会**被合并到词表里——它们只能按字甚至按 UTF-8 字节切。"

> "`o200k_base`(GPT-4o / 4.1 / 5)训练语料里中文比例大幅提升,而且词表扩到了 20 万,BPE 跑出来'你好'、'世界'、'谢谢'、'今天'这些高频词组**理所当然地被合并成单 token**。结果就是同一句中文,token 数砍掉一半。"

> "这也解释了一个常被问的问题:'**为什么有时候模型会拆出奇怪的字符?**' 因为底层是 **byte-level BPE**——所有文本先转 UTF-8 字节,再按字节做 BPE。这样**连 emoji、生僻字、外文字符都能编码,永远不会出现'未知字符'**;代价是某些低频字符会被拆成多个字节级 token,看起来很碎。"

---

##### 一句话总结 BPE

> 【讲师讲稿】"如果今天 BPE 只让你们记一句话,就是这句——**BPE 是一个'按使用频率把字符片段打包成词表'的统计算法,高频组合压成 1 个 token,低频内容按更细颗粒切**。理解了这个,你就理解了为什么不同语种、不同领域、不同年代的模型,token 密度差别这么大。"

**经验法则**(让学员记住,**注意新旧 encoding 差异**):
- **英文**:1 token ≈ 4 字符 ≈ 0.75 个单词。
- **中文**(老 encoding,`cl100k_base`,GPT-3.5 / 原版 GPT-4):1 个汉字 ≈ 1~2 tokens,常见标点也 1 token。
- **中文**(新 encoding,`o200k_base`,GPT-4o / GPT-4.1 / GPT-5 系列):**常用词组被合并**,"你好"、"世界"这种 2 字常用词常常 1 token,折算 **0.3~0.6 token / 字**;生僻字、长尾词组仍可能 1~2 token / 字。
- **代码/符号**:大致与英文持平,空格和换行也算 token。

**现场演示**(请学员真的跑一次,数字以你机器输出为准):
```python
import tiktoken
enc = tiktoken.encoding_for_model("gpt-4.1")   # o200k_base
print(len(enc.encode("Hello world")))         # 2
print(len(enc.encode("你好,世界")))           # 3 ← "你好" / "," / "世界" 各 1 个
print(len(enc.encode("def add(a, b): return a+b")))  # ~10

# 对照:老 encoding 下的同一句中文
old = tiktoken.get_encoding("cl100k_base")
print(len(old.encode("你好,世界")))           # 6 (老 encoding,中文按字粒度更细)
```

> 【讲师讲稿】"看见没?**同一句中文**,新 encoding 是 3 个 token,老 encoding 是 6 个——**整整一半**。这背后是 OpenAI 从 GPT-4o 起换了 `o200k_base`,词表里专门收录了大量中文高频词组(你好、世界、谢谢…),所以**现代模型上中文 prompt 不再'天然贵一倍'了**——但也别就此放松警惕:**生僻领域、长尾词组、人名地名仍然按字细切**。算成本时,**亲自跑一遍 `tiktoken` 是唯一可靠的办法**,不要凭印象算。"

> "另一个常见误区:**很多博客的'中文 1 字 ≈ 2 token'是 2024 年以前的经验**,在新模型上已经不准。所以请大家在自己业务文本上跑一次实测,建立自己业务领域的'token 密度直觉'。"

**为什么 token 重要(三个原因)**:
1. **计费**:OpenAI / Anthropic 按 token 数定价,输入和输出价格不同(输出通常贵 2~5 倍)。
2. **上下文窗口**:模型能"看见"的总长度有上限,单位也是 token。
3. **速度**:输出 token 数 ≈ 延迟,因为模型是逐 token 生成的。

#### 3. 上下文窗口:LLM 的"桌面大小"(15 min)

1. **输出价格普遍是输入的 4~6 倍**(看每行的两列比值)——所以"让模型啰嗦"是高成本来源。
2. **同档位差 10~50 倍**——GPT-4.1 nano vs Claude Opus 4.8 输入差 50 倍,输出差 60 倍。**选型即省钱**。
3. **长上下文有"隐性税"**——GPT-5、Gemini 2.5 Pro 超过某阈值后单价翻倍;Anthropic Opus 也对 >200K 加价。**塞满 1M 不等于按 1M 单价付**。
4. **缓存(prompt cache)能省 80~90%**——所有家都支持,但触发条件不同(L35 详讲)。

> 【讲师讲稿】"窗口大≠免费——**你塞进去的 token 一样要付费**。比如 GPT-5.5 真塞满 1M 输入跑一次,$5 × 1 = **$5 一次调用**,还没算输出。所以'省 token'永远是工程必修课。"

> "再注意一个直觉:**便宜不一定真便宜**。DeepSeek-V4-Flash 看起来比 GPT-4.1 便宜 14 倍,但如果它在你任务上要多跑 3 步、每步多输出 2 倍 token,实际成本可能差不多。**选型必须配合 eval**(L31 详讲),否则就是赌博。"

**提问**:"Agent 为什么特别容易撑爆上下文?" → 引导出答案:每轮都把 thought + tool_calls + tool 结果全部拼回去,**多轮累积是指数级膨胀**。这是 L19 短期记忆课要解决的核心问题。

#### 4. 消息角色与请求结构(20 min)

讲师在 Playground 里现场构造一次请求,逐行讲解每个角色:

```json
[
  {"role": "system", "content": "你是一个严谨的助手"},
  {"role": "user",   "content": "北京天气?"},
  {"role": "assistant", "content": null, "tool_calls": [
     {"id": "call_1", "type": "function",
      "function": {"name":"get_weather","arguments":"{\"city\":\"北京\"}"}}]},
  {"role": "tool", "tool_call_id": "call_1", "content": "25°C 晴"},
  {"role": "assistant", "content": "北京今天 25°C 晴。"}
]
```

| Role | 用途 | 关键字段 |
|---|---|---|
| `system` | 设定 Agent 的人设、规则、约束、可用工具说明 | `content` |
| `user` | 真实用户输入 | `content` |
| `assistant` | 模型生成的回复;若调工具,`content` 为 null 但有 `tool_calls` | `content` 或 `tool_calls` |
| `tool` | 工具执行结果,**必须**带 `tool_call_id` 对应到 assistant 的 tool_calls | `tool_call_id`, `content` |

> 【讲师讲稿】"很多新手在写 Agent 时把工具结果回填成 `assistant` 角色,看起来好像也能跑,但模型会困惑——它不知道这段内容是它自己说的还是工具说的,后续 tool_calls 的对齐也会乱掉。请大家记住:**工具结果就是 tool 角色,而且必须带 tool_call_id**,这是规范的硬要求。"

#### 5. 采样参数(15 min)

| 参数 | 含义 | Agent 推荐值 |
|---|---|---|
| `temperature` | 控制输出随机性。0=完全确定,>1=高度发散 | **工具调用阶段 0~0.3**;创意生成可 0.7 |
| `top_p` | 核采样,只在累积概率前 p 的候选里选 | 一般保持默认 1.0 |
| `max_tokens` | 单次最多输出多少 token | 按需限制,**防止模型一口气写 8000 字烧钱** |
| `frequency_penalty` / `presence_penalty` | 抑制重复 | 通用 Agent 可不调 |

> 【讲师讲稿】"为什么 Agent 的 temperature 推荐很低?因为我们要的是**模型稳定地选对工具、给对参数**,不要它发挥创意。temperature 一高,你会发现模型有时候选对工具有时候选错,调试时怀疑人生。0.0~0.3 是我自己常用的区间,生成最终回复时可以再调高一点。"

#### 6. 成本估算:现场算一次(10 min)

讲师举例:用上面表里 **GPT-4.1 当前真实单价 输入 $2/M、输出 $8/M**(2026-06 数据,讲师上课前请到 https://openai.com/api/pricing/ 核对)。

> 【讲师讲稿】"假设我们一次 Agent 调用,输入 5000 tokens、输出 1000 tokens,成本是:5000 × 2/1,000,000 + 1000 × 8/1,000,000 = $0.010 + $0.008 = **$0.018**(约 1.8 美分)。一次看起来不多对吧?但如果一个 Agent 一天跑 1000 次,就是 **$18/天,$540/月**。这才一个 Agent,一个用户。所以 L35 我们会专门讲降本,提前埋个伏笔。"

#### 7. 测查 + 小结(5 min)

### 六、板书设计
```
token: BPE 切分,英文 1 token≈4 字符
       中文 老编码(cl100k) 1 字≈1~2 token;新编码(o200k,GPT-4o/4.1/5)常用词组合并,1 字 ≈ 0.3~0.6 token
context window: 一张桌子,所有内容总长 ≤ 上限,超了硬截断
roles: system / user / assistant(可含 tool_calls) / tool(必须 tool_call_id)
sampling: agent 工具调用 temperature 0~0.3;max_tokens 必设
cost ≈ in × $A + out × $B  (B 通常 4~8×A,输出贵得多)
```

### 七、课堂练习(完整发放版)

> 讲师提示:本节练习需要**Python + tiktoken 已装好**(见教学准备)。学员每人一台笔记本即可,若没装 tiktoken 用[在线 tokenizer](https://tiktokenizer.vercel.app)也可。总时长 15-20 分钟,建议"独立做(10 min)→ 小组分享发现(5 min)→ 讲师汇总(5 min)"。

#### 练习 1:找出你自己 prompt 里的"token 大户"(10 min,个人)

**任务**:找一段你**过去 1 周真实用过**的 ChatGPT/Claude/Cursor 对话(约 200-500 字),用 tiktoken 分句计算每句的 token 数,找出 **top 3 最费 token 的句子** + 分析为什么。

**骨架代码**(直接粘贴运行):
```python
import tiktoken

encoder = tiktoken.get_encoding("o200k_base")

your_prompt = """
请把这里替换成你自己的一段真实 prompt 或对话。
建议 200-500 字,中英文混合更有意思。
如果贴了长文档也可以。
"""

sentences = [s.strip() for s in your_prompt.replace("\n", " ").split("。") if s.strip()]

results = []
for i, s in enumerate(sentences, 1):
    tokens = len(encoder.encode(s))
    chars = len(s)
    ratio = round(tokens / chars, 2) if chars else 0
    results.append((i, s[:40] + ("..." if len(s) > 40 else ""), chars, tokens, ratio))

results.sort(key=lambda r: r[3], reverse=True)

print(f"{'#':>3} | {'预览':<45} | {'字数':>5} | {'tokens':>7} | {'tok/字':>6}")
print("-" * 80)
for r in results[:5]:
    print(f"{r[0]:>3} | {r[1]:<45} | {r[2]:>5} | {r[3]:>7} | {r[4]:>6}")
```

**任务要求**:
1. 换上自己的 prompt 跑一遍
2. 记录 top 3 句子的"预览 + tokens + tok/字比"
3. 分析"为什么这几句最费"——常见原因:含长代码/长英文单词/URL/emoji/罕见汉字

**验收 checklist**:
- [ ] 跑出 top 5 排序表
- [ ] top 3 句子给出费 token 的具体原因(不是"因为长")
- [ ] 至少 1 个能优化的写法(如"这段代码可以放附件不放正文")

**参考答案样本**:
```
top 1:一段 URL "https://api.openai.com/v1/chat/completions" → 15 tokens / 43 字符
      原因:URL 每个符号(: / . )单独 tokenize
top 2:一段 Python trace(File "...", line 42, ...) → 32 tokens / 60 字符
      原因:非常规英文标识符(EncoderDecoder)拆得很细
top 3:表情符号 🎉🎉🎉 → 6 tokens / 6 字符
      原因:非 ASCII 字符每个 emoji 至少 1 tok,组合更贵
```

**常见坑**:
- 直接把整段代码贴 prompt 里 → 很费。**优化建议**:代码摘要 + 关键行,或用附件
- 反复重复 "请、麻烦、感谢" → 无信息 token,可裁
- 用 `cl100k_base` 编码 GPT-4o 的 prompt 会算错,GPT-4o/4.1 用 `o200k_base`

### 八、测查题与参考答案

#### 2. 工具 schema 一行行拆(20 min)

讲师把以下 schema 投影,逐行讲解:

```json
{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "Get current weather for a city. Use this when the user asks about today's weather.",
    "parameters": {
      "type": "object",
      "properties": {
        "city": {"type": "string", "description": "City name in English or Chinese"},
        "unit": {"type": "string", "enum": ["c", "f"], "default": "c"}
      },
      "required": ["city"]
    }
  }
}
```

逐字段讲:

- **`type: "function"`**:目前 OpenAI 工具类型主要是 function,后续可能扩展(retrieval、code interpreter)。
- **`name`**:工具的唯一标识符,代码层根据它分发到具体函数。**只能用字母数字下划线**,不要起花哨的名字。
- **`description`**:**模型选用这个工具的唯一依据**。写得不好,模型就不会调或调错。下面会重点演示。
- **`parameters`**:标准 JSON Schema。类型、必填、枚举、默认值都要写清楚。

> 【讲师讲稿】"我看过太多新手把 description 写成'a tool'或'查询工具',然后跑了几次发现模型不调用,就开始怀疑模型不智能。其实问题在你——模型每一步都在'我有 N 个工具,该选哪个'的选择题里挣扎,你给的 description 越清晰、越具体、越告诉它'什么时候该用我'、'什么时候不该用我',它就越容易选对。"

**description 写法三原则**:
1. **说明工具做什么**(动词开头,一句话讲清功能)。
2. **说明何时该用**("Use this when ...")。
3. **必要时说明何时不该用**("Do NOT use this for ...")。

#### 3. 现场对照实验:好 description vs 烂 description(20 min)

讲师在 Playground 跑两次同样的 prompt"北京天气怎么样":

**A 版**:description = `"Get current weather for a city. Use when the user asks about weather."`
- 模型主动返回 `tool_calls: [{"name":"get_weather","arguments":"{\"city\":\"北京\"}"}]`。

**B 版**:description = `"a tool"`

> 【讲师讲稿】"看见没?同样一个模型、同样一个 prompt,只改了 description 一行,行为完全不一样。**description 不是给人看的注释,是给模型看的'工作说明书'**。后面 L16 我们会发现 MCP 的 docstring 也是同样道理。"

#### 4. tool_calls 完整数据流(25 min)

画图(也作为板书):
```
1) user → LLM
2) LLM 输出 → 模型可能两种走法:
     a) 直接回答(content 有文本,tool_calls 为空)
     b) 想调工具(content 为 null,tool_calls 是一个列表)
3) 你的代码读到 tool_calls,逐个执行
4) 把每个工具结果以 role="tool" + tool_call_id 回填到 messages
5) 再次调 LLM
6) LLM 基于工具结果,输出 final answer(或再调工具,回到 3)
```

讲师逐步骤详细讲:

**步骤 2**:`tool_calls` 长这样(简化):
```python
[
  ToolCall(id="call_abc", function=Function(
    name="get_weather", arguments='{"city":"北京"}'))
]
```
注意 **`arguments` 是 JSON 字符串**,不是 dict。这是 OpenAI SDK 的反模式,90% 的新手会忘记 `json.loads`。

**步骤 4**:回填的格式必须严格:
```python
messages.append({
    "role": "tool",
    "tool_call_id": call.id,    # 一定要带这个,LLM 靠它对应到刚才哪次调用
    "content": str(result)       # 内容必须是字符串
})
```

**步骤 5**:**必须再调一次** `chat.completions.create`,模型才会基于工具结果生成最终自然语言回复。很多新手以为"工具调完就结束了",其实工具调完只是中间产物。

> 【讲师讲稿】"再强调一遍——function calling 的标准节奏是**两次 LLM 调用**:第一次模型决定调什么工具,第二次模型基于工具结果给最终回复。如果工具结果又触发模型调下一个工具,就是第三次、第四次……一直循环到模型不再返回 tool_calls 为止。这就是 L4 要讲的主循环。"

#### 5. 课堂找茬:3 段错误代码(10 min)

讲师投影 3 段代码,学员限时 5 分钟找 bug。

**Bug 1**:
```python
args = call.function.arguments         # 错!这是字符串
result = get_weather(**args)            # TypeError
```
**正确**:`args = json.loads(call.function.arguments)`

**Bug 2**:
```python
messages.append({"role": "assistant",   # 错!应该是 tool
                 "content": result})
```
**正确**:`role="tool"`,而且要带 `tool_call_id`。

**Bug 3**:
```python
for call in msg.tool_calls:
    ...
    messages.append({"role":"tool", ...})  # 漏了 msg 本身!
```
**正确**:先 `messages.append(msg)`(包含 tool_calls 的 assistant 消息),再 append 每个 tool 结果。否则模型看不到自己当初的 tool_calls,会一头雾水。

> 【讲师讲稿】"这三个坑我见过太多团队踩。Bug 3 最隐蔽——代码不报错,但模型会出现'我刚才说了什么我不知道'的诡异行为。务必牢记顺序:**assistant 消息(含 tool_calls)先入,然后每个 tool 结果入,再调下一次 LLM**。"

#### 6. 测查 + 小结(5 min)

### 六、板书设计
```
schema = name + description(模型选工具的依据) + JSON Schema parameters
flow:
  user → LLM ──(tool_calls)──▶ 代码 ──(API)──▶ 代码
                                                  │
                                                  ▼ role=tool, tool_call_id, content
                                          messages.append
                                                  │
                                                  ▼ 再调一次 LLM → final answer
trap:
  arguments 是字符串,先 json.loads
  回填 role=tool,带 tool_call_id
  msg(含 tool_calls)必须先 append
```

#### 挑战题(选做,7 min,留给做完练习 2 的学员)

把 schema 升级为 `convert_currency(amount, from_currency, to_currency, precision=2)`:

**新要求**:
1. `from_currency` 和 `to_currency` 用 **`enum`** 限定取值为 `["USD","CNY","EUR","JPY"]` 之一;
2. `precision` 是**可选参数**(default = 2),不放进 `required`;
3. description 必须包含一句 **"Do NOT use this for cryptocurrency"** 反向约束;
4. Python 端用 mock 函数实现(写死汇率即可,如 `{"USD->CNY": 7.1, ...}`);
5. 用 "100 美元换成人民币是多少" 提问,验证模型生成的 `tool_calls` 参数确实是 `{amount:100, from:"USD", to:"CNY"}`。

**关键答案要点**:
- `enum` 写在字段对象里:`{"type":"string","enum":["USD","CNY","EUR","JPY"]}`;
- 可选参数**只**在 `properties` 出现,**不**在 `required`;
- 描述里加 enum 之外仍要在 `description` 里**自然语言重述**一遍允许值,模型才会自觉遵守。

> 【讲师讲稿】"挑战题真正考的不是 enum 本身,而是**反向约束**的写法——你告诉模型'什么时候不该用我'比'什么时候该用我'更难。这是 L16 写 MCP docstring 时的高级技巧,先在这里埋个种子。"

### 八、测查题与参考答案

1. 模型"调用工具"时实际发生什么?  A. 模型直接发起 HTTP 请求调用 API  **B. 模型返回结构化 JSON 描述"要调什么 + 参数",由你的代码真正执行**  C. 模型内部已编译好工具函数,直接执行  D. 模型重写工具源码并运行 → **B**。Function calling 的本质——LLM 永远碰不到外部世界,执行层是代码。
2. tool description 越短越好吗?  A. 是,越短模型推理越快  **B. 否,过短(如 "a tool")模型会选不准甚至不调**  C. 无所谓,模型只看 `name`  D. 长度越长越好,越详细越准 → **B**。description 是模型选用工具的唯一依据,要写清"做什么/何时该用/何时不该用"。
3. 工具结果回填到 messages 时,`role` 字段应写什么?  A. `user`  B. `assistant`  **C. `tool`**(必须配 `tool_call_id`)  D. `system` → **C**。`role=tool` 是 OpenAI/Anthropic 规范的硬要求,必须带 `tool_call_id` 与上一条 assistant 消息里的某次调用对应。
4. **简答**:为什么模型"明明该调工具却编了答案"?
   - **参考答案**:① description 不清/不够具体;② temperature 太高;③ 模型版本不支持 tool use;④ system prompt 未强制要求使用工具;⑤ 工具列表太多稀释了模型注意力。
5. **编程**:补全 `add(a, b)` 工具调用代码(完整可运行,假设 `.env` 已配 `OPENAI_API_KEY`,以及可选 `OPENAI_BASE_URL` / `OPENAI_MODEL`)。

#### 2. Agent 经典架构图(20 min)

讲师重画 L1 的架构图,但这次每个组件都要展开说"它在循环里做什么":

```
        ┌─────────────────────────────────────────┐
        │                  AGENT                  │
        │                                         │
        │      ┌─────────┐         ┌─────────┐    │
        │      │   LLM   │ ◀────── │  Loop   │    │
        │      │  (大脑)  │ ──────▶│ (心跳)  │    │
        │      └─────────┘         └────┬────┘    │
        │           ▲                   │          │
        │  state    │                   ▼          │
        │      ┌────┴────┐         ┌─────────┐    │
        │      │ Memory  │         │  Tools  │    │
        │      │ (笔记本) │         │  (双手) │    │
        │      └─────────┘         └────┬────┘    │
        └───────────────────────────────│─────────┘
                                        ▼
                            外部 API / DB / 文件 / MCP
```

**逐组件讲它在循环里的角色**:

- **LLM(大脑)**:接收当前 state(主要是 messages 列表),输出"thought + 决定下一步"(以 tool_calls 或 final answer 体现)。
- **Loop(心跳)**:把"调用 LLM → 执行工具 → 回填结果"这三步反复跑,直到终止。
- **Memory(笔记本)**:**state 的载体**。短期 = 当前 messages 列表;会话 = 数据库;长期 = 向量库。每一步开始,LLM 从 Memory 里拿到完整上下文;每一步结束,把新产生的消息写回 Memory。
- **Tools(双手)**:外部能力的入口。每次执行一个 tool_call,产生一个 observation(工具结果),作为新消息进 Memory。

> 【讲师讲稿】"我希望大家把 Agent 想象成一个**带笔记本和工具的小人**:每一步他先看笔记本上写了什么(Memory),想一想下一步做什么(LLM),如果需要,就掏出工具去做(Tools),做完把结果写回笔记本(Memory),然后看着笔记本想下一步……直到他认为可以交付答案了。这就是 Agent 的全部。"

#### 3. 主循环伪代码:12 行讲透(25 min)

讲师在白板手写:

```python
def agent_loop(goal, max_steps=10):
    state = init_state(goal)              # 1. 初始化:把目标写进 messages
    for step in range(max_steps):         # 2. 心跳上限
        action = llm_decide(state)         # 3. 大脑决定下一步
        if action.is_final:                # 4. 是否给出最终答案?
            return action.answer
        obs = execute_tool(action)         # 5. 双手执行
        state = update(state, action, obs) # 6. 笔记本记下来
    return "max steps exceeded"           # 7. 兜底
```

**逐行讲解**:

- **第 1 行**:`init_state` 通常就是 `messages = [{"role":"system",...}, {"role":"user","content":goal}]`。
- **第 2 行**:`max_steps` 是 Agent 的**保险丝**。没有它,模型一旦陷入"反复调同一个工具"的死循环,就会一直烧钱。L11 我们会讲更完整的 guardrail。
- **第 3 行**:`llm_decide` 实际就是 `client.chat.completions.create(...)`。它的输出可能是 final answer,也可能是 tool_calls。
- **第 4 行**:**终止条件 1**——模型主动结束。`is_final` 在 OpenAI 里对应 `msg.tool_calls is None`。
- **第 5 行**:执行工具。注意这里可能要处理**多个 tool_calls 并行**(L10 会展开)。
- **第 6 行**:把 assistant 消息(含 tool_calls)和每个 tool 结果都 append 到 messages。
- **第 7 行**:**终止条件 2**——达到 max_steps。这种情况要在日志里高亮告警。
- **额外**:**终止条件 3** 是 guardrail(预算超、安全策略触发),L28 会讲。

**提问**:"为什么不写 `while True`?"
- 答:Agent 的 LLM 有时候会"卡住"——比如反复返回同一个 tool_calls,或者根本不肯输出 final。`while True` 等同于"愿意烧任意多钱",生产环境绝对禁止。

> 【讲师讲稿】"看见没?**模型不会主动放弃**——只要工具一直回错误信息,它就一直重试。如果我们没设 max_steps,你的 API bill 就会快速增长。所以即使写最简单的 demo,也务必把 max_steps 设上(我通常默认 10),这是肌肉记忆。"

**参考答案**:

```python
from openai import OpenAI
from dotenv import load_dotenv
import json, os, time
load_dotenv()

api_key  = os.getenv("OPENAI_API_KEY")
base_url = os.getenv("OPENAI_BASE_URL") or None
assert api_key, "未读到 OPENAI_API_KEY"
client = OpenAI(api_key=api_key, base_url=base_url)
MODEL  = os.getenv("OPENAI_MODEL", "gpt-4.1")

def get_weather(city: str) -> str:
    return f"{city} 今天 25°C 晴"

TOOL_REGISTRY = {"get_weather": get_weather}
TOOL_SCHEMAS = [{"type":"function","function":{
    "name":"get_weather",
    "description":"Get today's weather for a city.",
    "parameters":{"type":"object",
                  "properties":{"city":{"type":"string"}},
                  "required":["city"]}}}]

def run_agent(user_input: str, max_steps: int = 5) -> str:
    messages = [{"role":"user","content":user_input}]
    for step in range(max_steps):
        t0 = time.time()
        resp = client.chat.completions.create(
            model=MODEL, messages=messages, tools=TOOL_SCHEMAS)
        msg = resp.choices[0].message
        messages.append(msg)
        if not msg.tool_calls:                              # 正常出口
            print(f"[step {step}] FINAL: {msg.content[:60]} ({(time.time()-t0)*1000:.0f}ms)")
            return msg.content
        calls_summary = ", ".join(
            f"{c.function.name}({c.function.arguments})" for c in msg.tool_calls)
        print(f"[step {step}] TOOL_CALLS: {calls_summary}")
        for call in msg.tool_calls:
            fn = TOOL_REGISTRY.get(call.function.name)
            try:
                args   = json.loads(call.function.arguments)
                result = fn(**args) if fn else f"unknown tool: {call.function.name}"
            except Exception as e:
                result = f"ERROR: {type(e).__name__}: {e}"
            messages.append({"role":"tool", "tool_call_id":call.id, "content":str(result)})
    print(f"[step {max_steps-1}] MAX_STEPS_REACHED")
    return "max_steps exceeded, no final answer"            # guardrail 兜底

print(run_agent("上海和北京今天天气怎么样?"))
```

**评分要点**:
1. 每 step 打印 `step_idx` + tool_calls 或 final 摘要(可观察);
2. `max_steps` 触底也要 return 兜底字符串(不能 `None`);
3. 工具异常 `role=tool` 写回 messages(不 raise);
4. assistant 消息先入栈,再 append tool 结果(顺序不能错)。

### 六、板书设计
```
init_state ─▶ [LLM decide] ─▶ final? ─yes─▶ return
                    │
                    ▼ tool_calls
              [execute_tool] ─▶ update(state) ─▶ 回到 LLM
              (循环 max_steps 次)
终止 = final | max_steps | guardrail
```

```python
client = OpenAI()

def price(model, in_tok, out_tok):
    if model == "gpt-4.1": return in_tok/1_000_000*2.5 + out_tok/1_000_000*10

def run_dangerous(user_input):
    messages = [{"role":"user","content":user_input}]
    total_cost = 0.0
    step = 0

        resp = client.chat.completions.create(model="gpt-4.1", messages=messages, tools=TOOLS)
        u = resp.usage
        total_cost += price("gpt-4.1", u.prompt_tokens, u.completion_tokens)
```

**验收 checklist**:
- [ ] `while True` 替换为 `for step in range(max_steps)` 或加 `if step >= max_steps: break`
- [ ] `total_cost > MAX_COST_USD` 时立即退出并打印警告(不是继续 loop)

```python
MAX_STEPS = 8
MAX_COST_USD = 0.10

def run_safe(user_input):
    messages = [{"role":"user","content":user_input}]
    total_cost = 0.0
    last_answer = None

    for step in range(MAX_STEPS):
        resp = client.chat.completions.create(model="gpt-4.1", messages=messages, tools=TOOLS)
        u = resp.usage
        total_cost += price("gpt-4.1", u.prompt_tokens, u.completion_tokens)

        if total_cost > MAX_COST_USD:
            return f"[budget exceeded ${total_cost:.4f}] partial: {last_answer or '(none)'}"

        msg = resp.choices[0].message
        messages.append(msg)
        if msg.content:
            last_answer = msg.content
        if not msg.tool_calls:
            return msg.content

        for call in msg.tool_calls:
            args = json.loads(call.function.arguments)
            result = REGISTRY[call.function.name](**args)
            messages.append({"role":"tool","tool_call_id":call.id,"content":str(result)})

    return f"[max_steps={MAX_STEPS} exceeded] partial: {last_answer or '(none)'}"
```

- 把"文本式 ReAct"的字段对应到 function calling 的字段。

### 三、教学重点与难点
- **重点**:ReAct 的"循环 + 反馈"心智模型。
- **难点**:让学员区分"思考链(CoT)"和"思考-行动循环"——很多人混为一谈。

### 四、教学准备

**【教学素材】**
- **Yao 2022 论文 ReAct trace**(《ReAct: Synergizing Reasoning and Acting in Language Models》,arXiv:2210.03629):课前截取 HotpotQA 的经典 5 步 trace(Thought/Action/Observation 交替),打印或投影。
- **同一任务的 CoT-only 输出**做对照:让 GPT-4.1 用 CoT 模式(不给 tools)回答同一个多跳问题(如"Apple Remote 最初为哪款 Front Row 软件设计?"),记录它的推理链——**通常会幻觉**,让学员看到"没工具校验,推理错了没法自我发现"。
- **同一任务的 ReAct-with-tools 输出**:同样问题给一个 `wikipedia_search(query)` mock,让 LLM 用 ReAct 走 3-5 步。

**【代码素材】**
- **ReAct 格式 system prompt**(五.2 讲):文本式 ReAct 5 角色(Thought/Action/Action Input/Observation/Final Answer)完整 prompt 模板 + 1 个 example。
- **一段 5.4 demo 脚本**:用 gpt-4.1 + 一个假 `search` tool,让它跑"PM2.5 现在多少"这类需要联网的问题——**对比不加工具时它编造 vs 加工具后它调用**,视觉冲击最强。
- **对照 CoT-only 脚本**:同 model 同 prompt 但去掉 tools 参数,同问题看它编造。

**【数据 / 样例】**
- **3 类查询**用于演示:
  1. **时效性**:"上海此刻 PM2.5?" — 必须查
  2. **多跳事实**:"XXX 电影的导演另一部作品叫什么?" — 需分步查
  3. **计算**:"3241 × 5789 = ?" — 应调 `calculator` 不心算
- **典型 ReAct 失败 case**:一段 Action 名与 Tool schema 不一致的 trace(模型输出 `Action: search_wiki` 但工具叫 `wikipedia_search`),用于讲"Action 名严格对齐"。

**【教学材料】**
- **CoT vs ReAct 对比表**:2 列 4 行(定义 / 何时用 / 弱点 / 何时该升级),五.3 板书用。
- **ReAct 5 角色示意图**:Thought / Action / Action Input / Observation / Final Answer,标注"谁生成"(LLM 3 个 + 代码 1 个 + LLM 收尾 1 个)。

**【学员课前】**
- 熟悉 L3 的 function calling 数据流(assistant.tool_calls → tool 结果 → assistant.final)。
- 想 1 个自己"最容易被模型幻觉答错"的问题,课上 5.5 现场用 ReAct 跑一遍看是否改善。

**【备用方案】**
- 若 wikipedia_search API 不通 → 用**本地文件 grep** 作为 tool 演示(更快、更可控)。
- 若 CoT 幻觉那次没触发(gpt-4.1 有时会说"我不知道") → 换用小模型(如 Ollama 上的 llama3.2:latest)更容易幻觉,对比效果更强。

### 五、教学过程

#### 1. 导入(5 min)

> 【时间分配】0:00–0:30 暖场举手 | 0:30–3:00 现场双跑对照(普通 prompt vs ReAct prompt)| 3:00–4:00 把"反馈循环"钉成 ReAct 核心 | 4:00–5:00 学习产出承诺。

**(0:00–0:30) 暖场举手**

讲师投影一个具体问题:

> **"今天北京的 PM2.5 是多少,适不适合户外跑步?"**

举手统计:"如果你直接把这句话丢给 ChatGPT,你预计会得到——
(A) 准确的实时数值;
(B) 看起来合理但其实是它编的数字;
(C) 它告诉你'我无法实时查询'直接拒答?"

通常答案分裂在 B 和 C 之间,极少有人选 A。讲师不评价,留悬念。

> 【讲师讲稿】"今天要解决的就是这个困局——**怎么让一个'只会生成文本'的 LLM,获得'查真实数据 + 基于真实数据再推理'的能力**。这就是 ReAct 模式。下面我现场跑两次,你们对比着看。"

---

**(0:30–3:00) 现场双跑对照**

讲师在 OpenAI Playground 或自己的 demo 脚本里**真实跑两次**(没法联网时提前录好截图)。

**Run 1:普通 prompt(无 ReAct,无工具)**

```
User: 北京今天 PM2.5 是多少,适不适合户外跑步?
```

模型典型输出(几乎一定会出现的幻觉):
> "北京今天 PM2.5 大约在 45~60 之间,属于良好水平,适合户外跑步,记得做好热身……"

讲师追问全班:"这个数字是真的吗?" 答案是——**编的**,模型既没联网也不知道今天的真实值。

**Run 2:ReAct prompt + 一个工具**

system prompt 改成:

```
你是一个 ReAct agent。每一步必须按以下格式输出:
  Thought: <你的推理>
  Action: <工具名,或 "Finish">
  Action Input: <JSON 参数>
收到 Observation 后,继续下一个 Thought,直到给出 Final Answer。

可用工具:
  get_air_quality(city: str) -> {"pm25": int, "level": str}
```

讲师手动(或让代码)注入 Observation,模型典型输出:

```
Thought: 用户问北京 PM2.5,这是实时数据,我不能编,应该调 get_air_quality。
Action: get_air_quality
Action Input: {"city": "北京"}
Observation: {"pm25": 87, "level": "轻度污染"}

Thought: PM2.5 是 87,属于轻度污染,不适合长时间户外跑步。
         我可以给用户最终建议了。
Final Answer: 北京今天 PM2.5 为 87,属于轻度污染,不建议户外跑步。
             建议改为室内健身、瑜伽或瑜伽馆跑步机。
```

讲师并排投影两次输出,指着对比:

> 【讲师讲稿】"看这两次输出——
> - **Run 1** 模型在'假装知道',编了个数字,自信地告诉你'适合户外跑步'。如果你信了出门跑一小时,可能就白吸了一肺颗粒物。这就是**幻觉的真实危害**。
> - **Run 2** 模型先'想(Thought)'、再'做(Action)'、再'看结果(Observation)'、再'想'、最后才给答案。每一步推理都基于**真实数据**,结论跟着数据走,不是跟着'猜'走。
>
> 同一个模型、同一个问题,**只改了 prompt 范式**,行为完全不一样——这就是为什么 ReAct 值得专门花一节课讲。"

---

**(3:00–4:00) 把"反馈循环"钉成 ReAct 核心**

讲师在白板写下最简形式:

```
Thought ──▶ Action ──▶ Observation ──▶ Thought ──▶ Action ──▶ Observation ──▶ ... ──▶ Final Answer
   ▲                                       │
   └─────────────── 反馈回路 ──────────────┘
```

> 【讲师讲稿】"ReAct 这三个英文词里,**最容易被忽略的是 Observation**。很多人以为 ReAct = Reasoning + Action,精确说法应该是——
>
> **Reasoning + Acting + _Observing_ 的循环。**
>
> 因为如果没有 Observation,模型相当于'闭眼工作'——它发出去 Action,但永远不知道结果对不对、要不要换思路。Observation 是把**真实世界的反馈灌回模型上下文**的唯一通道——它是 ReAct 区别于 CoT 的**根本机制**。
>
> 2022 年姚顺雨等人在 ReAct 论文里用 HotPotQA、ALFWorld 等多个 benchmark 实验证明:**ReAct 准确率显著高于纯 CoT 和纯 Action**——核心原因就是 Observation 让模型能**从错误中纠正**。
>
> 今天市面上你见到的 **LangGraph、CrewAI、OpenAI Agents SDK,几乎所有 Agent 框架的主循环都是 ReAct 的变体**。它是 Agent 时代的事实标准——L6 会带大家看选型,L23 会讲它的进阶版 Plan-Execute,L24 会讲再进阶的 Reflexion,但**所有这些都基于今天讲的同一个循环骨架**。"

讲师把白板上的图圈起来,**全节课不擦**,作为后面 5.2~5.4 的视觉锚点。

---

**(4:00–5:00) 学习产出承诺**

> 【讲师讲稿】"这节课结束时,大家应该能做到三件具体的事——不是模糊的'理解',是**回工位就能写代码**的能力:
>
> 1. **手写一段文本式 ReAct 的 system prompt**——能让任意一个模型按 Thought / Action / Observation 节奏输出。
> 2. **说清 ReAct 与 CoT、Plan-Execute 的本质区别**——下次跟同事讨论时不再混为一谈,而是能精确指出'差在反馈循环上'。
> 3. **理解为什么现代实现都用 function calling 而不是文本正则**——这是'本质思想不变,实现形式升级'的典型工程演化,M2 写第一个 Agent 时大家就要用上。
>
> 第一步我们就来精讲 ReAct 的文本格式,看每一行到底是**谁**生成的——这是 90% 的学员搞不清的关键点。"

#### 2. ReAct 文本格式精讲(20 min)

完整 trace 示例:
```
Question: 北京今天天气怎么样?

Thought: 用户问北京天气。这是需要实时数据的问题,我不能凭印象编答案,
         应该调用 get_weather 工具,城市参数填"北京"。
Action: get_weather
Action Input: {"city": "北京"}
Observation: {"temp": 25, "condition": "晴", "humidity": "60%"}

Thought: 我已经拿到了天气数据,信息足够,可以给出最终回答了。
Final Answer: 北京今天 25°C 晴,湿度 60%。
```

**逐行讲解谁负责生成**:

| 行 | 来源 | 说明 |
|---|---|---|
| `Question:` | 用户输入 | 一开始注入 |
| `Thought:` | **LLM 生成** | 模型自己的推理 |
| `Action:` | **LLM 生成** | 模型决定调哪个工具 |
| `Action Input:` | **LLM 生成** | 模型决定的参数(JSON) |
| `Observation:` | **代码注入** | 你的代码执行工具后,把结果写回 |
| 第二个 `Thought:` | **LLM 生成** | 看了 observation 后的再思考 |
| `Final Answer:` | **LLM 生成** | 终结循环的标志 |

> 【讲师讲稿】"注意一个微妙的关键点:`Observation` 是**代码注入的**,不是模型自己生成的。这就是 ReAct 的精髓——**模型的思考(Thought)** 和 **真实世界的反馈(Observation)** 在 prompt 里交错,模型每一步推理都基于真实数据。这跟 CoT(只有思考链)是本质区别。"

---

#### 3. ReAct vs CoT vs Plan-Execute(20 min)

| 范式 | 思考 | 工具 | 反馈循环 | 适合场景 |
|---|---|---|---|---|
| **CoT** | 有("Let's think step by step") | 无 | 无 | 纯推理(数学题、逻辑题) |
| **ReAct** | 有 | 有 | **有,每步反馈影响下一步** | 通用 Agent,环境不确定 |
| **Plan-and-Execute** | 一次性规划全部步骤 | 按计划执行 | 弱(失败才 replan) | 多步且依赖明确,信息充分 |

**重点对比 CoT 与 ReAct**:

> 【讲师讲稿】"CoT 是'纯脑内推理'——模型说'让我一步步想……',但全部基于它已经知道的内容。如果中间需要真实数据,它只能编。ReAct 不一样,它每一步都可以**真的去执行**,看到真实结果再继续推理。所以 ReAct 是 CoT 的'有手版'。"

**重点对比 Plan-Execute 与 ReAct**:

> "Plan-Execute 是一开始就让模型规划好所有步骤,然后逐步执行。它的好处是**结构化、可观测**,坏处是**信息不充分时容易计划错**,因为规划阶段模型还没看到任何工具结果。ReAct 反过来,**每一步都基于最新信息决策**,容错强,但对长任务来说步数多、上下文增长快。L23 我们会专门讲什么时候该升级到 Plan-Execute。"

---

#### 4. 现代实现:从文本到 function calling(20 min)

讲师对比两种实现:

**早期文本式**(Yao 2022 论文原版):
```python
prompt = REACT_TEMPLATE + history + "Thought:"
output = llm.generate(prompt, stop=["Observation:"])
# 用正则解析 Action 和 Action Input
action = re.search(r"Action: (\w+)", output).group(1)
action_input = re.search(r"Action Input: (.+)", output).group(1)
```

**问题**:
- 正则非常脆弱,模型偶尔输出格式不对就 crash。
- 解析逻辑要自己维护,跨模型不兼容。

**现代 function calling 式**:
```python
resp = client.chat.completions.create(model=..., messages=..., tools=...)
msg = resp.choices[0].message
# tool_calls 直接是结构化数据,无需解析
for call in msg.tool_calls:
    action = call.function.name
    action_input = json.loads(call.function.arguments)
```

**好处**:
- 结构化,SDK 直接给你对象。
- 模型经过 fine-tune,**保证**输出格式正确(或返回 null 让你处理)。
- 跨模型(OpenAI、Anthropic 都有类似机制)。

> 【讲师讲稿】"所以请大家**不要再写正则解析 ReAct 文本了**——除非是面试/教学。生产代码一律用 function calling。Anthropic 叫 `tool_use`,逻辑一样。从文本到结构化,是 LLM 应用的一个重要进步。"

**字段对应**:
- 文本 `Thought:` → 现在合并进 `assistant.content`(可选,有些场景模型仍会输出思考过程)。
- 文本 `Action:` → `tool_calls[i].function.name`。
- 文本 `Action Input:` → `tool_calls[i].function.arguments`(JSON 字符串)。
- 文本 `Observation:` → `messages.append({"role":"tool", ...})`。

#### 6. 测查 + 小结(10 min)

**测查(7 min)**:投影第八节 3 道选择题,逐题学员**举手抢答**(30 秒思考),公布答案后讲师针对每题陷阱**点 1 句**——尤其第 1 题"Observation 是代码注入的"是 ReAct 与 CoT 的本质区别,务必反复强调。简答与场景题作为课后练习,讲师可在下节课开场抽问。

**小结(3 min)**:讲师投影 "今天必须带走的 3 句话",**口头复述一遍**:

> **今天必须带走的 3 句话**:
> 1. **ReAct = Reasoning + Acting + _Observing_ 循环**——Observation 是把真实世界灌回模型的唯一通道,缺它就退化成 CoT 的幻觉。
> 2. **ReAct ≠ CoT(无工具反馈)≠ Plan-Execute(先全局规划)**——三者各有适用场景,选错会"用大炮打蚊子"或"开赛车走山路"。
> 3. **现代实现用 function calling 替代文本正则解析**——本质循环结构不变,但格式正确性、跨模型兼容性都由 SDK 保证,生产首选。

> 【讲师讲稿】"今天讲的循环是 M2 你要亲手敲的骨架——文本式 ReAct 让你看见'幕后是什么',function calling 是它的'生产形态'。M5 还会带大家进阶到 Plan-Execute 和 Reflexion,但根都在今天这张图上。"

#### 7. 作业(5 min)
- 用文本式 ReAct 写一段 system prompt,让模型在没有 function calling 的情况下,也能按 ReAct 格式输出。下节课前提交。

**参考答案(sample system prompt)**:

```
You are a helpful assistant. You MUST follow the ReAct format strictly:

Thought: (你的思考过程,1~2 行)
Action: (工具名,只能从下面列表选)
Action Input: (传给工具的参数,JSON 格式)
Observation: (代码注入的工具结果,你不要自己写)
... (可以重复 Thought→Action→Action Input→Observation 多轮) ...
Thought: I now know the final answer
Final Answer: (给用户的自然语言回复)

可用工具:
- get_weather(city: str) → 返回指定城市今日天气
- now_time() → 返回当前 UTC 时间

规则:
1. 任何输出都必须是上述格式之一(Thought / Action / Action Input / Observation / Final Answer),不能混入散文段落。
2. **不要** 自己编 Observation,等代码注入下一轮。
3. 不知道答案时调工具,**绝不**编造。
4. 调用工具最多 5 轮,超过请直接给 Final Answer 并说明放弃理由。

示例:
User: 上海现在几点,天气怎么样?
Thought: 我需要先知道现在时间,再查上海天气。
Action: now_time
Action Input: {}
Observation: 2026-06-09T14:30Z
Thought: 现在 UTC 14:30,即上海 22:30。再查天气。
Action: get_weather
Action Input: {"city": "Shanghai"}
Observation: Shanghai 25°C 晴
Thought: I now know the final answer
Final Answer: 现在上海时间约 22:30,天气 25°C 晴。
```

**评分要点**:
1. 显式给出 Thought / Action / Action Input / Observation / Final Answer **5 个角色**;
2. **显式声明 Observation 由代码注入**(否则模型很容易自编 Observation 把整个轨迹幻觉一遍);
3. 给一个完整 example(few-shot,模型按格式输出的命中率会从 ~60% 提升到 >95%);
4. 强制止步条件(max 轮数或不知道→放弃,防死循环)。

### 七、课堂练习(完整发放版)

> 讲师提示:本节练习 3 题,前 2 题课上做(角色扮演 + trace 改写),第 3 题作为课后延续。所需仅纸笔即可完成前 2 题,第 3 题可选跑代码。

#### 练习 1:ReAct 角色扮演(15 min,2 人小组)

**任务**:两人一组,A 扮 **LLM(大脑)**,B 扮 **执行者(Tools + Observer)**,现场跑 3 轮 ReAct,把 Thought/Action/Observation 逐句说出来。

**任务清单**(选一个,任务本身不要太复杂,3-5 步能完成):
- 任务 A:"上海此刻 PM2.5 多少?空气质量在国内什么水平?"
- 任务 B:"《流浪地球 2》的导演另一部作品豆瓣评分多少?"
- 任务 C:"如果我现在从北京出发去杭州,坐高铁大约几点到?"

**可用工具**(限定,B 只能提供这几种"信息"):
- `search_web(query)` → 返一段模拟搜索摘要
- `now_time()` → 返当前时间
- `calculator(expr)` → 返算术结果

**规则**:
- A 每轮必须**先出声说** `Thought: ...`,再说 `Action: {tool}` + `Action Input: {args}`
- B 收到 Action 后**用尽量真实的口吻**给一段 `Observation: ...`(可以现场编造合理数据)
- 3-5 轮后 A 必须输出 `Final Answer: ...`
- 全程用**中文口播**,不写代码

**产出**:每组把 trace 写在 A4 纸上,格式:
```
Thought 1: 我需要先知道当前 PM2.5,应该 search
Action 1:  search_web("上海 PM2.5 实时")
Observation 1: (B 编) 上海 PM2.5 32 μg/m³,空气优
Thought 2: 32 已经很好,再对比国内平均
Action 2:  search_web("国内城市 PM2.5 排名 2026")
Observation 2: (B 编) 全国均值 45,上海排前 15%
Thought 3: 已经有足够信息
Final Answer: 上海此刻 PM2.5 是 32,空气优,好于全国 85% 城市
```

**验收 checklist**(讲师巡场检查):
- [ ] A 每轮都有 Thought(不是直接 Action)
- [ ] Action 名和 args 严格符合"可用工具"清单,不能编 `search_wikipedia`(工具没有)
- [ ] Observation 由 B 提供,A 不能自己"想象"结果
- [ ] 3-5 轮内出 Final Answer
- [ ] Final Answer 用到了至少 2 个 Observation 的内容

**常见坑**:
- A 一开始就想 Final(跳过 Thought)→ 讲师提醒"你必须先说 Thought"
- A 编造工具名(如 `wikipedia`) → B 应该拒绝并返 `Observation: [ERROR: tool not exists]`,考验 A 的 replan
- Observation 太理想化,A 没触发"需要更多信息"的思考 → 讲师引导 B 有时给"不确定"或"部分匹配"

#### 练习 2:CoT trace 改写为 ReAct(10 min,个人)

**任务**:下面是一段 **CoT(纯思考、无工具)** 的输出。请把它**改写为 ReAct 格式**,该调工具的地方用 Action 代替"我记得"。

**原始 CoT 输出**:
```
用户问:苹果公司 2024 年营收是多少?
LLM:
让我想想。苹果公司在 2024 年发布过财报,我记得 iPhone 收入约占 55%,
服务收入增长了 20%,总营收应该在 3800 亿美元左右。
最终答案:苹果 2024 年营收约 3800 亿美元。
```

**问题**:这段 CoT 的答案是**幻觉**——LLM"记得"的数字可能错。请改写为 ReAct 让它必查。

**改写要求**:
1. 用 Thought/Action/Observation/Final Answer 格式
2. 至少调 1 次 `search_web` 拿到权威数据
3. 若 search 结果不确定,允许再调 1 次(细化 query)
4. Final Answer 必须引用具体数据来源

**参考答案**:
```
Thought 1: 用户问的是苹果 2024 年营收。这是时效性数据,我不能靠记忆,必须查权威来源。
Action 1: search_web("Apple 2024 fiscal year annual revenue")
Observation 1: (来自 apple.com/newsroom) Apple 2024 财年(截止 2024-09-28)总营收 $391.0 billion
Thought 2: 拿到官方数据了。用户可能想知道日历年 vs 财年区别,但先给财年数据最稳。
Final Answer: 根据苹果 2024 财年年报(截止 2024-09-28),总营收为 $391.0 billion(约 3910 亿美元),来源:apple.com/newsroom。
```

**验收**:
- [ ] 至少 1 个 Action(search_web)
- [ ] Observation 明确引用来源(不是"我知道")
- [ ] Final Answer 引用具体数据 + 来源
- [ ] Thought 里体现"我不能靠记忆"的自觉

**常见坑**:改写后仍在 Thought 里凭空写数字("我估计...") —— ReAct 的价值在于**用工具校验**,不允许 Thought 假装知道未验证的事实

#### 练习 3(课后作业):为你自己的项目写一段 ReAct system prompt(选做)

**任务**:如果你的项目要接入 ReAct 循环,写一段完整的 system prompt,包含:
- 角色(who am I)
- 可用工具(2-4 个,用你项目真实的)
- 输出格式约束(严格 Thought/Action/... 五段式)
- 何时说 Final Answer(何时不能)
- 边界(哪类问题应该拒绝而不是硬答)

**参考模板**:见本课作业参考答案。

**验收**:同 M1 L5 作业。

### 八、测查题与参考答案

1. ReAct 中 `Observation` 指什么?  A. 模型对自己思考过程的复盘  **B. 工具被执行后真实返回的结果(由代码注入,不是模型生成)**  C. 用户给 Agent 的反馈  D. 系统监控指标 → **B**。Thought / Action / Action Input 都是 LLM 生成,只有 Observation 是代码注入——这是 ReAct 的精髓。
2. 与 CoT(Chain-of-Thought)相比,ReAct **多了**什么?  A. 更长的推理链  **B. 实际工具执行 + 真实反馈循环**  C. 更高的 temperature  D. 多模态输入 → **B**。CoT 全在脑内推理(易幻觉),ReAct 每步可执行真工具拿真数据。
3. 现代 ReAct 实现首选哪种方式?  A. 让模型按文本模板输出,用正则解析 `Action:`、`Action Input:`  **B. 用原生 function calling / tool_use,SDK 直接给结构化对象**  C. 让模型输出 XML 后 XPath 解析  D. 用 fine-tune 一个专门的解析模型 → **B**。正则解析脆弱跨模型不兼容;function calling 已成事实标准,SDK 保证格式。
4. **简答**:为什么 ReAct 比 Plan-Execute 更适合不确定任务?
   - **参考答案**:ReAct 每步基于最新 observation 调整,环境不确定时容错强;Plan-Execute 在初始信息不足时易计划错,且没 Replanner 兜底后续全错。
5. **场景**:写文本式 ReAct 的 system prompt。
   - **参考答案**:
     ```
     You are a ReAct agent. For each step, output exactly:
     Thought: <your reasoning>
     Action: <tool name, or "Finish">
     Action Input: <JSON arguments>
     After receiving Observation, continue with Thought again,
     until you can output:
     Final Answer: <your answer>
     ```

### 九、教学反思要点
- 学员有没有把 ReAct 和 CoT 搞混?可以再举一道纯推理题让学员判断该用谁。
- 角色扮演非常有效,务必保留(很多学员第一次"用身体懂"了 Agent 循环)。

## L6 — 主流 Agent 框架对比与选型

### 一、基本信息
- **课时编号**:L6
- **课时时长**:90 分钟
- **课型**:理论 + 决策训练
- **前置**:L1–L5
- **教具**:框架对比表、3 个真实业务场景卡片、决策树图。

### 二、教学目标
**知识目标**
- 列出至少 5 个主流 Agent 框架及核心定位。
- 复述"何时不用框架"的判断标准。

**能力目标**
- 给定一个业务需求,3 分钟内做出选型决策,并写出 1 条核心理由。
- 能反驳"上来就用最复杂框架"的工程冲动。

### 三、教学重点与难点
- **重点**:选型决策树 + "够用就好"的工程美学。
- **难点**:克服"上来就上最热门框架"的工程师本能。

### 四、教学准备

**【教学素材】**
- **框架对比表**(五.3 已内嵌完整表):OpenAI Agents SDK / LangGraph / CrewAI / LlamaIndex Agents / Cursor SDK / 手写 6 家,对比 5 个维度:抽象层级 / 学习曲线 / 状态管理 / 生态成熟度 / 适用场景。**课前核对 2 个月内是否有版本变化**(LangGraph、CrewAI 迭代快)。
- **3 张业务场景卡片**(A5 打印,分组讨论用),讲师可换成本团队真实需求:
  1. "只需给 GitHub PR 自动加 3 行摘要" → 应选**手写**,不上框架
  2. "客服 Agent,10 个工具,3 层审批,失败要断点续跑" → 应选 **LangGraph**(HITL + checkpoint)
  3. "研究报告 Agent:分析师 + 写手 + 校对 3 角色并行" → 应选 **CrewAI 或 LangGraph**(多角色)
- **过度工程反面案例**(五.1 导入用,故事化):
  - 案例 A(过度):某团队 3 人上来就上 LangGraph + Redis Checkpoint + Langfuse + eval pipeline,做一个"每天生成一段 tech news 摘要"的简单任务,2 周还没 demo。**结论**:20 行手写 + cron 就够了。
  - 案例 B(欠工程):某团队做客服 Agent 全手写,3 个月后被 HITL + 断点恢复需求逼疯,大规模重构。**结论**:一开始就该上 LangGraph。

**【数据 / 样例】**
- **决策树板书**(五.4 用):
  ```
  步骤 ≤5 且工具 ≤3 ─▶ 手写
  复杂状态/HITL      ─▶ LangGraph
  全 OpenAI 生态     ─▶ OpenAI Agents SDK
  RAG 主导           ─▶ LlamaIndex
  多角色协作         ─▶ CrewAI
  IDE 内嵌           ─▶ Cursor SDK / 直接用现成产品
  ```

**【教学材料】**
- **一句话选型口诀**:"能手写就别上框架,能 SDK 就别上 LangGraph"(反向抵抗过度设计本能)。
- **"何时升级到框架"3 个 trigger**:① 需要 HITL 审批 ② 需要 state 断点恢复 ③ 多个 Agent 协作 ——五.4 讲。

**【学员课前】**
- 回忆 L1 作业里自己的"要改造的流程",今天要给它做框架选型 + 决策理由(L6 作业)。
- 熟悉 M1 L2-L5 讲过的技术栈(function calling / ReAct / 主循环),这决定"手写"到底能扛多复杂。

**【备用方案】**
- 若学员对某框架完全没概念(如 LangGraph 从未看过) → 用 mermaid 现场画一个"StateGraph 节点=函数 边=条件"的示意图,3 分钟建立直觉,足够本课判断"这个场景需不需要它"。
- 若讨论环节倾向 "全部要用最强框架"(过度设计倾向) → 讲师祭出反面案例 A,并追问"这周就能上线的最简版本长什么样?" —— 强迫团队从最小可行版本反推。

#### 2. 主流框架地图(25 min)

**逐个框架讲,每个框架用"一句话定位 + 优点 + 缺点 + 适合谁"四段式**。

##### 2.1 OpenAI Agents SDK(Python / TypeScript)

- **一句话**:OpenAI 官方推出的 Agent 框架,围绕 Assistants API 设计。
- **优点**:官方维护、function calling 最稳、内置 handoff(Agent 间任务移交)、文档齐全。
- **缺点**:绑定 OpenAI 生态,换 Claude / 本地模型时迁移成本高。
- **适合**:已经全用 OpenAI 的团队、PoC 阶段图省事。

##### 2.2 LangGraph(Python / TypeScript,LangChain 生态)

- **一句话**:把 Agent 描述成"状态图(StateGraph)",节点是函数、边是条件。
- **优点**:复杂循环、分支、多 Agent 协作天然适配;有 checkpoint 支持暂停/恢复(HITL 利器);与 LangSmith trace 深度集成。
- **缺点**:学习曲线陡(状态机思维不是所有人都习惯);代码量比 OpenAI SDK 多。
- **适合**:任务复杂、有显式工作流、需要 HITL 或多 Agent 的生产场景。

##### 2.3 CrewAI(Python)

- **一句话**:多 Agent 角色协作框架,主打"team of agents"(队长 + 队员)。
- **优点**:多角色 Agent 写起来很自然;有任务委派、角色描述等高层抽象。
- **缺点**:抽象层次偏高,出问题时不易调优;社区相比 LangGraph 小一些。
- **适合**:确实需要多个 Agent 各司其职的业务(如"研究员 + 写手 + 编辑")。

##### 2.4 LlamaIndex Agents(Python)

- **一句话**:LlamaIndex 的 Agent 模式,把 RAG 与 Agent 深度整合。
- **优点**:RAG / 文档检索是它强项,索引、retriever、reranker 一站式。
- **缺点**:偏向文档场景,通用 Agent 能力相对窄。
- **适合**:任务以"读大量文档后回答/操作"为主(如法律、医疗、内部知识库)。

##### 2.5 Cursor SDK / `@cursor/sdk`(TypeScript)

- **一句话**:把 Cursor 的编码 Agent 能力封装成 SDK,可在自己代码里调用。
- **优点**:复用 Cursor 已有的代码理解能力;TS 优先。
- **缺点**:仅 TS;场景偏编码自动化。
- **适合**:做"AI 编码 / 代码改造"类工具。

##### 2.6 手写(任意语言)

- **一句话**:不用任何框架,自己组装 LLM 调用 + 工具 + 循环。
- **优点**:零依赖、完全可控、学习收益最大、上线包最小。
- **缺点**:工具注册、记忆、可观测、重试……都得自己写。
- **适合**:学习阶段、Demo、超简单任务(≤5 步,工具 ≤3 个)、边缘部署对依赖体积敏感的场景。

> 【讲师讲稿】"框架的成熟度、社区活跃度、文档质量,长期看比'功能多寡'更重要。一个半死不活的框架,出 bug 时你找不到人。所以选型时,**优先选社区大、维护活跃、文档清楚的**——目前 LangGraph 和 OpenAI Agents SDK 是两个比较安全的选择。"

**示例卡片**:
1. "做一个 GitHub PR 评审助手,读取 diff 后给建议,关键建议要审批后才留言。"
   - **建议**:LangGraph(需要 HITL 暂停-恢复)。
2. "周末写个小脚本,定时检查我关注的几个开源项目有没有新 release。"
   - **建议**:手写(工具就一两个,流程固定,Workflow 即可)。
3. "做一个研究助手,先去网上搜文献,再让一个 Agent 写综述,另一个 Agent 校对。"
   - **建议**:CrewAI 或 LangGraph(多角色)。

#### 4. 何时不用框架 + 反面案例(15 min)

> 【讲师讲稿】"我见过太多团队为一个 100 行的脚本引入 LangGraph,理由是'怕以后扩展'。结果半年后项目废弃,LangGraph 的依赖、配置、学习成本全白费。请记住:**当下需求 + 未来 3 个月可见需求** 是选型边界,**不要为'万一'付费**。"

**何时不用框架**:
1. 任务步数 ≤5、工具 ≤3、流程固定。
2. PoC、Demo、学习项目。
3. 部署到边缘/嵌入式环境,依赖体积敏感。
4. 公司明确禁止某种依赖(合规、安全)。

**反面案例**:展示一个"为简单任务用 LangGraph"导致 5 倍代码量的对比,直接让学员看 diff。

#### 5. 测查 + 小结(10 min)

**测查(7 min)**:投影第八节 3 道选择题,**学员举手抢答**,公布答案后讲师针对每题陷阱**点 1 句**。**重点**强调第 3 题——"手写最大代价是基础设施全自己造",这呼应了导入故事 B(欠工程案例)。简答与场景题作为课后练习。

**小结(3 min)**:讲师投影"今天必须带走的 3 句话"——其中第 1 句就是导入时白板正中那句话,**全节课闭环回收**:

> **今天必须带走的 3 句话**:
> 1. **框架选型 = 匹配"当前需求 + 未来 3 个月可见需求"**,不是"用最酷的",也不是"框架是束缚"。
> 2. **决策树**:≤5 步 / ≤3 工具 → 手写;复杂状态 / HITL → LangGraph;全 OpenAI 生态 → OpenAI Agents SDK;RAG 主导 → LlamaIndex;多角色协作 → CrewAI。
> 3. **5 个主流框架的一句话定位记住**,这是技术 leader 跟同事交流时的"通用语"。

> 【讲师讲稿】"M1 到此结束。从下节课 M2 开始,我们用今天选定的'手写 + function calling'路线,亲手敲第一个 Agent——不上任何框架,先把 L4 那 12 行循环跑通,再逐步加工具、加 retry、加并发。M5 我们会带大家进入 LangGraph,届时你会感受到'今天选不选 LangGraph'这个决策的真实代价。"

#### 6. 作业(5 min)
- 回到 L1 作业里"自己想改造的流程",给出框架选型 + 一段决策理由(至少 100 字)。

**参考答案(范文示例,接续 L1 客服 Agent 例子)**:

> 选 **LangGraph**。理由:
> ① 该 Agent 有 6 个工具且涉及"查日志→召集 owner→重启服务"这种**条件分支**(读多写少 vs 读写并存路径不同),状态图比 if/elif 更清晰;
> ② `page_owner` / `post_to_slack` / `restart_service` 是**有副作用动作**,需要 HITL 审批,LangGraph 的 `interrupt_before=["page_owner", "restart_service"]` 是开箱即用的能力,手写要自己造审批中间件;
> ③ **checkpoint 持久化**能力让客户工单中途崩了也能续跑,这对 P1 工单尤其重要;
> ④ 团队 < 5 人,LangGraph 的学习曲线 1~2 周可吃下,且 LangSmith trace 能省下大量 debug 时间。
>
> **不选 OpenAI Agents SDK** 因为后续要支持 Claude 做某些工具(GPT 工具调用偶尔幻觉);**不选 CrewAI** 因为只有 1 个角色而非多角色协作;**不选纯手写** 因为 HITL 和 checkpoint 自造成本太高(估算 2~3 人周)。

**评分维度**(每项 2.5 分,共 10 分):
1. 给出**明确框架名**(非含糊"用框架"或"看情况");
2. 至少 **3 条具体理由**,且与该流程的需求(分支 / HITL / RAG / 多角色)挂钩;
3. 给出**"不选 X 的理由"**以体现对比思考;
4. 字数 ≥ 100 字且无空话(忌"框架强大""社区活跃"这种营销词)。

**任务**:阅读下面 5 个业务需求,给每个需求:

3. 用**1 句话**说"为什么不选另一个明显选项"

**5 个需求卡**:

| # | 需求描述 | 关键约束 |
| - | -------- | -------- |
| A | 给 GitHub PR 加 3 行 AI 摘要;每 PR 只跑 1 次,内部用 | 无 HITL、无长任务、每天 <100 次 |

**决策树参考**(讲师板书):

#### 练习 2:诊断 over/under-engineering(10 min,个人)

**任务**:阅读下面 2 段故事,判断是 **过度工程** 还是 **欠工程**,并给出**修正建议**(50 字内)。

**故事 A**:
> 某团队做"每天生成 200 字 tech news 摘要发到 Slack"。3 人花 2 周搭 LangGraph + Redis checkpoint + Langfuse trace + eval pipeline,还没跑通 hello world。CTO 拍桌。

**故事 B**:
> 某团队做客服 Agent,20 个工具、10 万日活。为了"快",全部手写:主循环、retry、budget、日志、HITL 审批面板、trace 全 from scratch。3 个月后:代码 8000 行,重构无从下手,新人 onboard 要 1 个月。

**你的答案**:

| # | 判断 | 修正建议 |
| - | ---- | ---- |
| A | | |
| B | | |

**参考答案**:

| # | 判断 | 修正建议 |
| - | ---- | ---- |
| A | **过度工程** | 20 行 `openai + cron + slack webhook` 即可,LangGraph 应等业务复杂度上来再上 |
| B | **欠工程** | 至少 HITL/checkpoint/trace 3 个模块应用 LangGraph + Langfuse 现成方案,自己聚焦业务逻辑 |

- 如果 A 和 B 都是"业务确定 3 个月后要扩 10 倍",判断会变吗?

### 八、测查题与参考答案

1. "分析师 + 写手 + 校对"三角色协作的 Agent,首选哪个框架?  A. OpenAI Agents SDK(handoff 模式也可,但更适合简单移交)  **B. CrewAI 或 LangGraph(原生支持多角色 / 多 Agent 协作)**  C. 手写 + asyncio  D. LlamaIndex Agents → **B**。CrewAI 主打"team of agents",LangGraph 用 StateGraph 也很合适;两者都对多角色场景有专门抽象。
2. LangGraph 相比其他 Agent 框架最显著的特色是?  A. 自带模型推理引擎  **B. 用 StateGraph 状态图描述循环 / 分支 / 多 Agent,节点是函数、边是条件**  C. 仅支持 GPT 系列模型  D. 内置向量数据库 → **B**。状态机思维 + checkpoint 持久化 + interrupt_before(HITL)是 LangGraph 的三大杀手锏。
3. 完全手写(不用框架)的最大代价是?  A. 模型推理变慢  **B. 工具注册 / 记忆 / 重试 / trace / HITL 都得自己实现,长期维护成本高**  C. 无法用 GPT-4 系列  D. 必须用 Python → **B**。零依赖、可控、轻量是手写的优点;代价是所有"框架免费给你的东西"都要自己造轮子。
4. **简答**:PoC "读 PDF 后回答问题",推荐哪个框架?
   - **参考答案**:**LlamaIndex Agents**。PDF + RAG 是它最强项,内置解析器/检索器/索引一站式。
5. **场景**:10 个 Agent 要统一可观测性和评估,选型应考虑什么?
   - **参考答案**:① 是否原生集成 Langfuse / LangSmith;② trace schema 是否统一;③ Evals 集成度;④ 多语言/多模型兼容性;⑤ 团队学习曲线;⑥ 社区活跃度与维护成本。
