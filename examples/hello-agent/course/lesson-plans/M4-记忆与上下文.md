### 五、教学过程

#### 1. 导入:为什么对话越聊越慢、越聊越贵(5 min)

讲师让一位学员描述"上次跟 ChatGPT 聊了很多轮,后来感觉越来越慢、有时候它甚至忘了开头说什么"的体验。

> 【讲师讲稿】"这背后是一个简单的事实:**Agent 的每一轮请求都把全部历史塞回去**。一开始 messages 只有 100 tokens,第 5 轮可能 3000 tokens,第 10 轮 8000 tokens……增长是非线性的。增长意味着三件坏事:① **更贵**(token 计费);② **更慢**(长 prompt 处理时间增长);③ **撞窗口上限**(直接报错或被自动截断)。"

> "今天我们就把'怎么管短期上下文'这件事讲透,并写出可直接用在生产代码里的工具函数。"

#### 2. 三种短期记忆策略对比(20 min)

讲师在白板列出对比:

| 策略 | 描述 | token 曲线 | 质量 | 实现复杂度 |
|---|---|---|---|---|
| **全量保留** | 保留全部 messages | 近似指数增长 | 最高(但常撞窗口) | 零(默认行为) |
| **滚动窗口 N** | 只保留最近 N 轮 | 几乎常数 | 早期细节丢 | 低 |
| **摘要 + 窗口** | 早期消息合并摘要 + 最近 N 轮原文 | 常数 + 摘要轻微增长 | 较高,推荐 | 中(需要摘要 LLM 调用) |

**逐策略详讲**:

**(1) 全量保留**

> 【讲师讲稿】"这是大多数 demo 代码的默认行为——L8/L9 我们写的代码就是这样,所有消息都 append 进 messages,从不删。短期看挺好,直到你跑到第 N 轮,API 报错 `context_length_exceeded`。这条路在生产里走不通。"

**(2) 滚动窗口**

```python
def trim_messages(messages, max_pairs=6):
    """保留 system + 最近 max_pairs 个 user/assistant 对话对"""
    system = [m for m in messages if m["role"] == "system"]
    others = [m for m in messages if m["role"] != "system"]
    # 简单截取最后 2 * max_pairs 条(一对 user + assistant)
    return system + others[-2 * max_pairs:]
```

> 【讲师讲稿】"看起来很粗暴,但实践中**这是 80% Agent 的默认选择**。原因是:**Agent 的决策依据主要来自最近的 thought 和 observation**,早期闲聊式信息对决策贡献小。所以扔掉早期内容,**反而降噪、提速、降本**。"

**坑**:工具消息(role=tool)必须跟它对应的 assistant 消息(含 tool_calls)成对出现。简单按个数截取可能切断这种对应,导致 API 报错。**完整实现要按"消息组"(assistant + 它产生的 tool 结果)切**:

```python
def trim_messages_safe(messages, max_groups=6):
    system = [m for m in messages if m["role"] == "system"]
    others = [m for m in messages if m["role"] != "system"]
    
    # 把 others 切成"组":每个 assistant + 它的 tool_calls 后续的 tool 结果是一组
    groups = []
    current = []
    for m in others:
        role = m["role"] if isinstance(m, dict) else m.role
        if role in ("user", "assistant") and current:
            groups.append(current)
            current = []
        current.append(m)
    if current:
        groups.append(current)
    
    return system + [m for g in groups[-max_groups:] for m in g]
```

**(3) 摘要 + 窗口**

把"窗口之外"的内容用一个轻量 LLM 调用摘要成一两段话,以 system message 形式插入。

```python
def summarize_old(old_messages):
    text = "\n".join(f"{m['role']}: {str(m.get('content',''))[:200]}"
                     for m in old_messages)
    resp = client.chat.completions.create(
        model="gpt-4.1-mini",
        messages=[{"role":"user",
                   "content": f"用 100 字内总结以下对话要点:\n{text}"}]
    )
    return resp.choices[0].message.content

def trim_with_summary(messages, max_recent=6):
    system = [m for m in messages if m["role"] == "system"]
    others = [m for m in messages if m["role"] != "system"]
    if len(others) <= 2 * max_recent:
        return system + others
    old, recent = others[:-2*max_recent], others[-2*max_recent:]
    summary = summarize_old(old)
    return system + [{"role":"system", "content": f"## 历史摘要\n{summary}"}] + recent
```

> 【讲师讲稿】"摘要 + 窗口是质量与成本的最佳平衡——早期信息以摘要形式保留,近期信息原文保留。缺点是需要额外的 LLM 调用做摘要(可以用 mini 模型省钱)。**对长会话或多轮任务,这是默认推荐**。"

#### 3. 用 tiktoken 精确计数(15 min)

讲师演示:

```python
import tiktoken
enc = tiktoken.encoding_for_model("gpt-4.1")

def count_tokens(messages):
    """近似计数(精确算法略复杂,但够用)"""
    total = 0
    for m in messages:
        if hasattr(m, "model_dump"):
            m = m.model_dump()
        content = m.get("content") or ""
        total += len(enc.encode(content))
        # tool_calls 等其他字段
        if m.get("tool_calls"):
            total += len(enc.encode(json.dumps(m["tool_calls"])))
    return total
```

让学员对自己 L9/L12 的对话日志计数,得出"我这次对话最高峰是 X tokens"。

> 【讲师讲稿】"知道自己的 token 增长曲线是优化前提。**没量化就不要谈优化**——这跟性能工程一模一样。后面 L35 我们做成本/性能优化,起点也是看 token 数据。"

#### 5. 测查 + 小结(15 min)

**测查(10 min)**:
1. 投影第八节 3 道选择题,**学员举手抢答**(30 秒思考),公布答案后讲师针对每题陷阱**点 1~2 句**——尤其第 3 题"用 `tiktoken` 才准"是新手"凭字符数估算"的盲点。
2. **简答 + 场景题**(第 4、5 题)分两组讨论 3 分钟,代表口头作答——场景题"每轮涨 2k token / 10 轮爆窗口"是真实生产高频问题,讲师补漏"长 tool result 替换占位符"这种高级招式。

**小结(5 min)**:讲师投影 "今天必须带走的 3 句话":

> **今天必须带走的 3 句话**:
> 1. **上下文窗口有硬上限,Agent 多轮容易爆**——`trim_messages` + 摘要是最常用治理手段,核心策略是**"压历史不压现在"**(早期细节用摘要,近期完整保留)。
> 2. **滚动窗口在很多 Agent 里效果意外地好**——Agent 决策主要依赖近期上下文,早期细节大多无关;质量损失通常可忽略,但响应速度 / 成本显著改善。
> 3. **永远用 `tiktoken` + 对应模型 encoding 精确算 token**,不要凭字符数估算——中英文比率不同,`cl100k_base` 与 `o200k_base` 又不同,凭感觉错得离谱。

> 【讲师讲稿】"今天讲的是'短期记忆'——单次会话内的上下文治理。L20 讲'会话级记忆'(跨进程恢复),L21 讲'长期记忆'(向量库召回)。三者构成 Agent 的完整记忆体系。回家写'全量 vs 摘要+窗口'两版对比,你会真实感受到 token 曲线的差异。"

```python
    stats    = []
    for i, ui in enumerate(user_inputs):
        messages.append({"role":"user","content":ui})
        t0   = time.time()
        resp = client.chat.completions.create(model=MODEL, messages=messages, tools=TOOL_SCHEMAS)

        messages.append(msg)
```

#### 练习 2:实现 `trim_with_summary` + 对比(25 min,个人)

**任务**:实现"滚动窗口 + 摘要"策略,让 tokens 稳定在 2000 上限内,同时不损失重要信息。

**函数签名**:
```python
def trim_with_summary(
    messages: list[dict],
    max_tokens: int = 2000,
    keep_recent: int = 4,          # 最近 N 条完整保留
    summarizer: callable = None,   # LLM 摘要函数(可选,内测可 mock)
) -> list[dict]:
    """
    - 若总 tokens ≤ max_tokens → 原样返回
    - 否则:
        1. 保留 system message(如有)
        2. 保留最近 keep_recent 条 messages
        3. 中间部分调 summarizer 压缩成 1 条 system 消息 "[summary of X turns]: ..."
    """
    ...
```

**验收 prompt 集**:同 10 轮固定脚本;分别用 3 个版本跑并记录:
- 版本 A:全量(baseline)
- 版本 B:滚动窗口(只留最近 4 条,不摘要)
- 版本 C:窗口 + 摘要(用 LLM 摘要中间轮)

**期望结果对比**:
| 轮次 | 版本 A tokens | 版本 B tokens | 版本 C tokens |
| ---- | ---- | ---- | ---- |
| 1 | 40 | 40 | 40 |
| 5 | 1200 | 400 | 500(含摘要) |
| 10 | 6000 | 400 | 500 |

**验收 checklist**:
- [ ] 3 个版本都能跑完 10 轮不 crash
- [ ] 版本 B、C tokens 稳定在 500-1500 之间
- [ ] 版本 C 的摘要不丢关键信息:第 10 轮问"帮我总结"仍能提到"3 天关西游、京都、大阪、奈良、预算 1 万"
- [ ] 版本 B 会**丢信息**:第 10 轮问"预算多少"可能答不出来(因为前面被切了)

**参考答案(核心)**:
```python
def trim_with_summary(messages, max_tokens=2000, keep_recent=4, summarizer=None):
    if count_tokens(messages) <= max_tokens:
        return messages

    # 分层
    system_msgs = [m for m in messages if m.get("role") == "system"]
    others = [m for m in messages if m.get("role") != "system"]

    if len(others) <= keep_recent:
        return system_msgs + others

    to_summarize = others[:-keep_recent]
    recent       = others[-keep_recent:]

    if summarizer is None:
        summary_text = f"[summary of {len(to_summarize)} earlier messages truncated]"
    else:
        summary_text = summarizer(to_summarize)

    return system_msgs + [{"role":"system","content":f"[Earlier conversation summary]\n{summary_text}"}] + recent

# LLM 摘要器
def llm_summarizer(msgs) -> str:
    text = "\n".join(f"{m.get('role')}: {m.get('content')}" for m in msgs)
    resp = client.chat.completions.create(
        model=MODEL,
        messages=[
            {"role":"system","content":"用 3-5 句话总结下面对话的关键信息(保留数字/地名/用户偏好):"},
            {"role":"user","content":text[:8000]},
        ],
    )
    return resp.choices[0].message.content
```

**常见坑**:
- 忘保留 system message → Agent 掉了角色定义
- keep_recent 太小(如 2)→ 用户提问上下文缺,LLM 答非所问
- summarizer 每轮都调 → 反而多花钱;应**只在超阈值时才调一次**
- 摘要用同一个大模型 → 太贵;可用 gpt-4o-mini 或 haiku 做摘要

| ---- | ---- | ---- | ---- |

### 八、测查题与参考答案

1. "上下文窗口硬上限"指的是?  **A. 单次 API 请求中 input + output 的 token 数不能超过模型最大窗口,否则报错或截断**  B. 模型每分钟最多处理的 token 数  C. 账户每月 token 配额  D. 一次最多输出的字数 → **A**。这是模型架构层面的硬约束,与计费、限流是不同维度。
2. 摘要(summarize)策略压缩历史时,主要损失的是?  A. 最近的 user 消息  **B. 早期细节(具体数字、原话引用、错误堆栈等被概括掉)**  C. system prompt  D. 工具列表 → **B**。摘要本质是"用更短的话讲同一件事",细节必然丢;所以重要事实要么 pin 在 system,要么落库另存。
3. 计算 messages 实际 token 数最准的方式是?  A. `len(text)`(字符数估算)  **B. 用 `tiktoken` 加载该模型对应的 encoding(如 `cl100k_base`/`o200k_base`)精确编码**(API usage 字段也准但要付费一次)  C. `len(text.split())`(按空格切词)  D. 模型大小除 1000 → **B**。本地用 `tiktoken` 离线算,不消耗 API 配额;不同模型 encoding 不同,务必用 `encoding_for_model(...)`。
4. **简答**:为什么"滚动窗口"在很多 Agent 里反而效果不错?

5. **场景**:每轮涨 2k token、10 轮爆窗口,3 种改造?

#### 2. Schema 设计:为什么不是一个 JSON 文件(20 min)

**反面方案**:`sessions/{user_id}.json`,每次读全文件、写全文件。

**问题**:
- 多进程并发写会冲突(竞态条件)。
- 大文件读写慢。
- 不能按时间 / 角色 / 工具 筛选。
- 不能做"删除最老 N 条"等结构化操作。

**正面方案:双表 schema**:

```sql
CREATE TABLE IF NOT EXISTS sessions (
    session_id  TEXT PRIMARY KEY,
    user_id     TEXT NOT NULL,
    title       TEXT,
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE IF NOT EXISTS messages (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id    TEXT NOT NULL,
    role          TEXT NOT NULL,
    content       TEXT,
    tool_call_id  TEXT,         -- tool 消息用
    tool_calls    TEXT,         -- assistant 消息可能含 JSON
    created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (session_id) REFERENCES sessions(session_id)
);

CREATE INDEX IF NOT EXISTS idx_messages_session ON messages(session_id, id);
```

**逐字段讲**:
- `sessions.session_id`:推荐 UUID,跨用户全局唯一。
- `sessions.user_id`:**核心隔离字段**。L22 的"多用户记忆"全靠它。
- `messages.role`:`system / user / assistant / tool`。
- `messages.tool_call_id`:tool 消息必须带,对应到 assistant 消息里某个 tool_call。
- `messages.tool_calls`:assistant 消息如果调了工具,这个字段存 JSON 序列化后的列表。
- `idx_messages_session`:按 session_id 查的索引,**没这个索引,千万级数据查询会慢**。

> 【讲师讲稿】"为什么不直接存 messages 整体 JSON?四个原因:① **可索引**——按 role/时间/tool 检索一秒返回;② **并发安全**——SQLite 自带锁,Redis 自带原子操作;③ **结构化操作**——'删除最老 10 条' 是一句 SQL,不需要读全文件;④ **可演进**——加字段不破坏旧数据。这是数据库相对于文件的根本优势。"

#### 3. CRUD 函数现场写(25 min)

```python
import sqlite3
import json
import uuid
from typing import List, Dict, Any

DB_PATH = "agent.db"

def _conn():
    conn = sqlite3.connect(DB_PATH)
    conn.row_factory = sqlite3.Row
    return conn

def init_db():
    with _conn() as c:
        c.executescript("""
        CREATE TABLE IF NOT EXISTS sessions (
            session_id TEXT PRIMARY KEY,
            user_id TEXT NOT NULL,
            title TEXT,
            created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        );
        CREATE TABLE IF NOT EXISTS messages (
            id INTEGER PRIMARY KEY AUTOINCREMENT,
            session_id TEXT NOT NULL,
            role TEXT NOT NULL,
            content TEXT,
            tool_call_id TEXT,
            tool_calls TEXT,
            created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        );
        CREATE INDEX IF NOT EXISTS idx_messages_session ON messages(session_id, id);
        """)

def get_or_create_session(user_id: str, session_id: str = None) -> str:
    sid = session_id or str(uuid.uuid4())
    with _conn() as c:
        c.execute("""INSERT OR IGNORE INTO sessions(session_id, user_id) 
                     VALUES (?, ?)""", (sid, user_id))
    return sid

def append_message(session_id: str, msg: Dict[str, Any]):
    """msg 可以是 dict 或 OpenAI 的 ChatCompletionMessage(有 .model_dump())"""
    if hasattr(msg, "model_dump"):
        msg = msg.model_dump(exclude_none=True)
    tool_calls = json.dumps(msg.get("tool_calls")) if msg.get("tool_calls") else None
    with _conn() as c:
        c.execute("""INSERT INTO messages(session_id, role, content, tool_call_id, tool_calls)
                     VALUES (?, ?, ?, ?, ?)""",
                  (session_id, msg["role"], msg.get("content"),
                   msg.get("tool_call_id"), tool_calls))

def load_messages(session_id: str) -> List[Dict]:
    with _conn() as c:
        rows = c.execute("""SELECT role, content, tool_call_id, tool_calls 
                            FROM messages WHERE session_id=? ORDER BY id""",
                         (session_id,)).fetchall()
    out = []
    for r in rows:
        m = {"role": r["role"]}
        if r["content"] is not None: m["content"] = r["content"]
        if r["tool_call_id"]:        m["tool_call_id"] = r["tool_call_id"]
        if r["tool_calls"]:          m["tool_calls"] = json.loads(r["tool_calls"])
        out.append(m)
    return out
```

**逐函数讲**:
- `init_db`:幂等(`IF NOT EXISTS`),可在每次进程启动时调一次,自动建表。
- `get_or_create_session`:支持"指定 session_id 恢复" 或 "新建"。
- `append_message`:**注意 `model_dump`**——OpenAI SDK 返回的 `msg` 是 Pydantic 对象,要先转 dict 才能 JSON 化。
- `load_messages`:按 id 升序还原原始顺序;**只 SELECT 用到的字段**,避免传输无关数据。

#### 5. SQLite vs Redis 简介(5 min)

| | SQLite | Redis |
|---|---|---|
| 部署 | 一个文件 | 独立服务 |
| 并发 | 文件锁(读多写少 OK) | 内存,极高并发 |
| 持久化 | 默认开启 | 默认开启(AOF / RDB) |
| 适合 | 单机原型、桌面应用、小型 SaaS | 高并发、分布式、多服务共享 |

> 【讲师讲稿】"我个人建议:**任何 PoC / 个人项目都从 SQLite 起步**,代码极简,部署零成本。需要扩到多个 worker / 多个服务共享时,再换 Postgres 或 Redis,业务代码动得很少。**不要为'未来万一'引入 Redis 复杂度**。"

```python
    conn.execute("INSERT INTO sessions VALUES (?,?,?)",
                 (sid, user_id, datetime.utcnow().isoformat()))
    conn.commit()
    return sid

def load_messages(conn, sid: str) -> list[dict]:
    rows = conn.execute("SELECT role, content, tool_call_id, tool_calls "
                        "FROM messages WHERE session_id=? ORDER BY id",
                        (sid,)).fetchall()
    msgs = []
    for role, content, tcid, tcalls in rows:
        m = {"role": role, "content": content}
        if tcid:   m["tool_call_id"] = tcid
        if tcalls: m["tool_calls"]   = json.loads(tcalls)
        msgs.append(m)
    return msgs

def save_message(conn, sid, msg: dict):
    conn.execute(
        "INSERT INTO messages(session_id,role,content,tool_call_id,tool_calls,created_at) "
        "VALUES (?,?,?,?,?,?)",
        (sid, msg["role"], msg.get("content"), msg.get("tool_call_id"),
         json.dumps(msg.get("tool_calls"), default=str) if msg.get("tool_calls") else None,
         datetime.utcnow().isoformat()))
    conn.commit()

def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--resume", help="session_id to resume; new if omitted")
    parser.add_argument("--user", default="default")
    args = parser.parse_args()

    conn = init_db()

    if args.resume:
        # 校验存在性
        if not conn.execute("SELECT 1 FROM sessions WHERE session_id=?", (args.resume,)).fetchone():
            print(f"❌ session {args.resume} not found")
            return
        sid = args.resume
        messages = load_messages(conn, sid)
        print(f"📂 Resumed session {sid}, {len(messages)} historical messages loaded.")
        print(f"   Last user msg: {next((m['content'] for m in reversed(messages) if m['role']=='user'), '<none>')[:80]}")
    else:
        sid = new_session(conn, args.user)
        messages = [{"role":"system","content":SYSTEM}]
        save_message(conn, sid, messages[0])
        print(f"🆕 New session {sid}")

    while True:
        user_input = input("\nyou> ").strip()
        if user_input in {"exit", "quit", ""}:
            break
        user_msg = {"role":"user","content":user_input}
        messages.append(user_msg)
        save_message(conn, sid, user_msg)

        reply = run_agent_step(messages)            # 复用 L9 主循环,但每步 save_message
        print(f"\nai> {reply}\n")

    print(f"\n💾 Session {sid} saved. Resume with:  python agent_cli.py --resume {sid}")

if __name__ == "__main__":
    main()
```

```python
import sqlite3, json
from typing import Any

def _get_conn(path="sessions.db"):
    conn = sqlite3.connect(path, check_same_thread=False)
    conn.execute("PRAGMA journal_mode=WAL")     # 支持并发读写
    return conn

def init_db(path="sessions.db"):
    conn = _get_conn(path)
    conn.executescript("""
        CREATE TABLE IF NOT EXISTS sessions (
            session_id TEXT PRIMARY KEY,
            user_id    TEXT,
            created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        );
        CREATE TABLE IF NOT EXISTS messages (
            id INTEGER PRIMARY KEY AUTOINCREMENT,
            session_id TEXT NOT NULL,
            role TEXT NOT NULL,
            content TEXT,
            tool_calls TEXT,
            tool_call_id TEXT,
            created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        );
        CREATE INDEX IF NOT EXISTS idx_session ON messages(session_id, id);
    """)
    conn.commit()
    conn.close()

def new_session(session_id, user_id="default", path="sessions.db"):
    conn = _get_conn(path)
    conn.execute("INSERT OR IGNORE INTO sessions(session_id,user_id) VALUES(?,?)",
                 (session_id, user_id))
    conn.commit()
    conn.close()

def append_message(session_id, msg, path="sessions.db"):
    # msg 可能是 openai 的 ChatCompletionMessage 对象,统一转 dict
    if hasattr(msg, "model_dump"):
        msg = msg.model_dump()
    content = msg.get("content")
    if isinstance(content, list):
        content = json.dumps(content, ensure_ascii=False)
    tool_calls = msg.get("tool_calls")
    tc_str = json.dumps([tc if isinstance(tc,dict) else tc.model_dump() for tc in tool_calls],
                        ensure_ascii=False) if tool_calls else None
    conn = _get_conn(path)
    conn.execute(
        "INSERT INTO messages(session_id,role,content,tool_calls,tool_call_id) VALUES(?,?,?,?,?)",
        (session_id, msg["role"], content, tc_str, msg.get("tool_call_id"))
    )
    conn.commit()
    conn.close()

def load_messages(session_id, path="sessions.db"):
    conn = _get_conn(path)
    rows = conn.execute(
        "SELECT role,content,tool_calls,tool_call_id FROM messages WHERE session_id=? ORDER BY id ASC",
        (session_id,)
    ).fetchall()
    conn.close()
    result = []
    for role, content, tc, tcid in rows:
        m = {"role": role}
        if content:
            m["content"] = content
        if tc:
            m["tool_calls"] = json.loads(tc)
        if tcid:
            m["tool_call_id"] = tcid
        result.append(m)
    return result
```

**常见坑**:
- 未开 `PRAGMA journal_mode=WAL` → 多进程并发写会 `database is locked`
- `tool_calls` 直接 `str(...)` 存 → 反序列化失败
- 忘记 `ORDER BY id ASC` → messages 顺序错乱,LLM 报格式错

### 八、测查题与参考答案

1. 为什么需要"会话级记忆"(把 messages 持久化到 SQLite/Redis 等)?  A. 让模型输出更快  **B. 跨 API 请求 / 进程重启后能恢复对话状态,且支持多会话隔离**  C. 节省 API 费用  D. 让 LLM 学会用户偏好(那是 long-term memory) → **B**。进程内内存只活在一次 Python run 里;HTTP/Bot 等"请求-响应"模型必须落库才能续聊。
2. 选 SQLite 还是 Redis?  **A. 单机原型 / 嵌入式选 SQLite;高并发、分布式、跨服务共享选 Redis**  B. 始终用 Redis  C. 始终用 SQLite  D. 不重要,效果一样 → **A**。SQLite 零运维、文件级、ACID;Redis 真正的网络服务、高并发友好,支持 TTL/pub-sub,适合多实例 Agent 服务。
3. messages 持久化表里**必备**的字段是?  **A. `session_id`(区分对话)+ `role` + `content` + 时间戳**  B. 只需 `content`  C. 只需 `user_id`  D. 只需 `tool_name` → **A**。`session_id` 是恢复"哪段对话"的钥匙;`role` 用于回填 messages 时还原原始结构。
4. **简答**:为什么不直接存整个 messages JSON 而要分表?
   - **参考答案**:① 按 role/时间/tool 检索;② 单条增删安全(并发友好);③ 利于摘要/向量化/分析;④ 避免大字段更新锁整行;⑤ 可加字段不破坏旧数据。
5. **场景**:连续 50 轮、表膨胀,如何治理?
   - **参考答案**:① 老消息(如 7 天前)合并摘要并归档到 `messages_archive` 表;② 压缩或删除大型 tool 结果;③ 加复合索引;④ 引入归档机制冷存;⑤ 长期可分库分表或迁 Postgres + 分区。

#### 2. 核心概念精讲(30 min)

##### 2.1 Embedding

**定义**:把一段文本映射到一个**固定长度的向量**(如 1536 维),向量空间的相似度近似语义相似度。

**为什么有用**:
- 给定一段 query,可以快速找到"语义最近"的若干文档,而不是只能 keyword 匹配。
- 计算便宜(矩阵运算),适合大规模。

**模型选择**:
- OpenAI `text-embedding-3-small`(1536 维,便宜,推荐起步)。
- OpenAI `text-embedding-3-large`(3072 维,精度更高,贵)。
- 本地:`bge-large-zh`(中文场景)、`m3e-base`。

##### 2.2 Chunking(切片)

**为什么不能整篇 embed**:
- 一篇 1 万字的文章,整篇生成一个向量,**语义被平均化**,失去局部信息。
- 检索时无法定位到具体段落,只能整篇返回。

**经验值**:
- chunk size:**200~800 tokens**(中文)。
- overlap:**10%~20%**(防止重要句子被切断)。

**简单实现**:
```python
def chunk_text(text, chunk_size=400, overlap=80):
    chunks = []
    i = 0
    while i < len(text):
        chunks.append(text[i:i+chunk_size])
        i += chunk_size - overlap
    return chunks
```

##### 2.3 Top-k 与 Reranker

**Top-k**:检索时返回最相似的 k 个 chunk,k 通常 3~10。
- k 太小:可能错过相关内容。
- k 太大:噪声多,稀释 prompt 上下文。

**Reranker**:用更强的模型(如 Cohere Rerank、BGE-Reranker)对 top-k 结果**重排**,挑出最相关的 top-3。是 RAG 后期优化的常用招数。

##### 2.4 RAG vs Fine-tuning

| | RAG | Fine-tuning |
|---|---|---|
| 加新知识 | 立即(写入 vector DB) | 需要重训 |
| 成本 | 低(只多一次检索) | 高(数据 + GPU) |
| 可追溯 | 是(可附引用) | 难 |
| 改风格 | 难 | 强项 |
| 适合 | 知识库、长期记忆 | 行为模式、特定输出风格 |

> 【讲师讲稿】"今天讲的所有'长期记忆',都是 RAG 范畴。Fine-tuning 是另一条路,代价大但能改模型行为本身。**绝大多数场景 RAG 已经够用,先 RAG 不行才考虑 fine-tune**——这是工程通则。"

```python
import chromadb
import uuid, os
from openai import OpenAI
from dotenv import load_dotenv
load_dotenv()

api_key  = os.getenv("OPENAI_API_KEY")
base_url = os.getenv("OPENAI_BASE_URL") or None
assert api_key, "未读到 OPENAI_API_KEY"
oai = OpenAI(api_key=api_key, base_url=base_url)
EMB_MODEL = os.getenv("OPENAI_EMB_MODEL", "text-embedding-3-small")

# ⚠️ **embedding 模型选型对中文场景至关重要**:
#   - `text-embedding-3-small`(OpenAI, 1536d)  ✅ 多语言, 中文 top-1 命中 ~95%
#   - `bge-m3`(BAAI 多语言, 1024d)             ✅ 中文 top-1 命中 ~100%(Ollama 可拉)
#   - `qwen3-embedding`(阿里, 1024d)            ✅ 中文超强
#   - `nomic-embed-text`(英文优化, 768d)       ❌ 中文命中率仅 ~20%, **生产慎用**
# 真实实测:同样 10 条中文记忆 + 5 个查询, nomic 召回 1/5, bge-m3 召回 5/5.
# 选模型不要只看维度数, 要看训练语料是否覆盖目标语言.

chroma = chromadb.Client()   # 内存版,持久化用 chromadb.PersistentClient(path="./chroma_db")
# 注意:chromadb 1.5+ 严格校验 collection 名:必须 3-512 字符, 只允许 [a-zA-Z0-9._-],
# 且**首尾必须是字母数字**——`_memory` / `memory-` 都会抛 InvalidArgumentError, 推荐 snake-case 或短横线.
collection = chroma.get_or_create_collection("memory")

def embed(text: str) -> list[float]:
    resp = oai.embeddings.create(model=EMB_MODEL, input=text)
    return resp.data[0].embedding

def remember(text: str, meta: dict = None):
    """把一条文本入库"""
    collection.add(
        ids=[str(uuid.uuid4())],
        embeddings=[embed(text)],
        documents=[text],
        metadatas=[meta or {}],
    )

def recall(query: str, k: int = 5, where: dict = None) -> list[str]:
    """召回最相关的 k 条"""
    res = collection.query(
        query_embeddings=[embed(query)],
        n_results=k,
        where=where,
    )
    return res["documents"][0]
```

**讲解关键点**:

- `chromadb.Client()` vs `chromadb.PersistentClient(path)`:**前者内存,进程退出就没了**;生产用后者。
- `embeddings=[embed(text)]`:必须传**列表的列表**(Chroma 支持批量)。
- `metadatas`:用来存"这条记忆是谁的、什么时候的、什么类型"等结构化字段,**支持过滤**。
- `where={"user":"alice"}`:Chroma 的 metadata 过滤,L22 多用户隔离的核心。

**学员实操 25 分钟**:
1. 灌入 10 条 FAQ 或对话摘要。
2. 跑 3 个查询,看 top-3 返回是否相关。
3. 用 metadata 区分两个虚拟用户的数据,验证 `where` 过滤生效。

```python
BASE_SYSTEM = "你是 Alice 的私人助手。"

    messages = [{"role":"system","content":system},
                {"role":"user","content":user_input}]
    
    # 3. 跑主循环……(略)
    answer = ...
    
    # 4. 这次的对话也存进长期记忆
    summary = f"User: {user_input}\nAssistant: {answer}"
    remember(summary, meta={"user": user_id, "ts": time.time()})
```

**为什么放 system 而不是 user**?

> 【讲师讲稿】"如果把召回结果拼到 user 末尾,会**污染用户的原话语义**——模型可能以为用户在转述这些内容。放到 system 里,作为'背景资料',模型会理解这是参考信息,**不会与用户的真实意图混淆**。这是一个细节但很重要的最佳实践。"

```python
    coll = get_collection()
    meta = {"user_id": user_id, **(metadata or {})}
    coll.add(ids=[doc_id], documents=[text], embeddings=[embed(text)], metadatas=[meta])

    coll = get_collection()
    res = coll.query(query_embeddings=[embed(query)], n_results=k,
                     where={"user_id": user_id})
    docs = res["documents"][0]
    dists = res["distances"][0]
    metas = res["metadatas"][0]
    return [{"text":d, "distance":dist, "metadata":m} for d,dist,m in zip(docs,dists,metas)]
```

### 八、测查题与参考答案

1. embedding(向量化)的本质是?  A. 把文本压缩成 zip 二进制  **B. 用模型把文本映射成稠密浮点向量,语义相近的文本在向量空间里距离也近**  C. 把文本翻译成英文  D. 给文本打标签 → **B**。embedding 是 RAG 的基石——之后用余弦相似度 / 内积找"最像"的片段。
2. RAG 系统的效果瓶颈**通常**出在哪里?  A. LLM 推理能力  **B. 文档 chunking 切分质量 + 检索召回准确度(选错 chunk 一切白搭)**  C. 向量库的硬盘 I/O  D. 模型 temperature → **B**。"垃圾进、垃圾出"——chunk 切得不好 / 召回不准,LLM 再聪明也答不对。
3. 把检索到的 chunk 拼入 LLM prompt,最常见的位置是?  A. `assistant` 消息  **B. `system` 消息末尾(也可拼到当前 `user` 消息末尾,用 "参考资料:..." 区分)**  C. `tool` 消息  D. 模型 logit_bias → **B**。放 system 表示"这是背景知识、要参照";放 user 末尾表示"这是这一轮的参考"。两者都常见,看场景。
4. **简答**:为什么 chunk size 不能太大也不能太小?
   - **参考答案**:太大→语义不聚焦(被平均化),检索精度下降、单条 token 多;太小→碎片化,上下文不完整,LLM 拿不到足够信息回答。经验 200~800 tokens + 10%~20% overlap。
5. **场景**:召回总返回不相关结果,原因 + 调优?
   - **参考答案**:① chunk 不当(过大/过小/没 overlap);② embedding 模型与中文语料不匹配(用 `bge-large-zh`);③ query 信息太少(用 HyDE 让 LLM 先扩写假答案再 embed);④ top-k 设置不当;⑤ 缺 metadata 过滤(用户/时间);⑥ 加 reranker 二次排序。

### 九、教学反思要点
- "拿铁 vs 咖啡 vs 股票"的向量距离演示效果决定整节直观度,务必提前跑通。
- 时间不够时,reranker 留作延伸阅读;chunking 与 query 扩展更优先。

**核心整合代码(`agent.py`)骨架**:
```python
from stm import trim_with_summary, count_tokens
from session_store import init_db, new_session, append_message, load_messages
from ltm import recall, remember

MAX_STM_TOKENS = 2000

def run_step(user_input, session_id, user_id):
    # TODO 1:加载长期记忆
    memories = recall(user_input, user_id, k=3)
    memory_prompt = "已知记忆:\n" + "\n".join(f"- {m['text']}" for m in memories) if memories else ""

    # TODO 2:加载中期(SQLite)
    history = load_messages(session_id)

    # TODO 3:组装 messages
    messages = [{"role":"system","content":"You are a helpful personal assistant."}]
    if memory_prompt:
        messages.append({"role":"system","content":memory_prompt})
    messages.extend(history)
    messages.append({"role":"user","content":user_input})

    # TODO 4:应用短期 trim,再喂 LLM
    messages = trim_with_summary(messages, max_tokens=MAX_STM_TOKENS, keep_recent=4)

    # LLM 调用 + tool 循环(继承 M2)
    reply, new_msgs = call_llm_loop(messages)

    # 写中期
    append_message(session_id, {"role":"user","content":user_input})
    for m in new_msgs:
        append_message(session_id, m)

    # (可选)提取"关键事实"入长期
    fact = extract_fact_if_any(user_input, reply)
    if fact:
        remember(doc_id=f"{user_id}-{time.time()}", text=fact, user_id=user_id,
                 metadata={"source":"auto","session":session_id})

    return reply
```

**`extract_fact_if_any` 建议实现**(简化版):用 LLM 判断"这条对话是否包含用户偏好或关键事实",返 None 或 str。

### 八、测查题与参考答案

1. 多用户场景下 RAG 召回为什么必须按 `user_id` metadata 过滤?  A. 加速查询  **B. 防止串号——用户 A 的私有记忆不能被检索到用户 B 的对话中(隐私 + 安全)**  C. 节省存储  D. 让模型更聪明 → **B**。这是多租户 Agent 的生死线,缺一个 `where={"user_id": uid}` 就是重大隐私事故。
2. 把超长对话/历史先用 LLM 摘要再写入向量库,主要好处是?  **A. 节省存储 + 节省检索后塞回 prompt 的 token + 提升召回密度(单条信息含量更高)**  B. 让向量更精确  C. 完全替代原始数据  D. 加速 embedding 计算 → **A**。摘要后 chunk 更精炼,top-k 召回回更多有效信息,但要保留原始一份以便溯源。
3. 多用户长期记忆**最容易出隐私事故**的环节是?  **A. 向量库跨用户共用 collection 但召回时忘加 `where` 过滤,导致跨用户串号**  B. embedding 模型本身  C. SQLite 文件权限  D. system prompt 写错 → **A**。多数事故不是恶意,是默认行为没改——所有用户共享一个 collection、检索时全表扫,自然串号。
4. **简答**:embedding 模型升级了,旧向量怎么办?
   - **参考答案**:不同模型向量空间不可比,**必须重嵌全部历史**;过渡期可双写双查再切换;迁移过程中冻结新写入或加版本号区分。
5. **场景**:用户问"上次聊到哪了",召回的是别人的内容,排查方向?
   - **参考答案**:① `recall` 是否带 `user_id` metadata filter;② ID 大小写/格式是否一致(`alice` vs `Alice`);③ 数据库是否多用户共用 collection 未隔离;④ `remember` 的 metadata 是否真的写入了 user_id;⑤ embedding 时是否带 user 前缀污染(应该不带)。

### 九、教学反思要点
- 多用户互验是这节的高潮,必须留够时间。
- 串号反面案例非常深刻,务必现场演示一次"故意忘加 where" 的串号场景,让学员看到隐私风险。
- 把这个"有记忆助手"作为 M5 引入 Plan-Execute 的输入素材。
