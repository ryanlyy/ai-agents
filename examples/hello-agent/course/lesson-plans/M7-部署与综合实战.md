#### 2. 5 种部署形态精讲(25 min)

##### 2.1 CLI 脚本

**适合**:个人自动化、运维巡检、一次性任务。

**典型实现**:
```python
# cli.py
import argparse
import asyncio
from agent import run_agent

def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("task")
    parser.add_argument("--user", default="default")
    args = parser.parse_args()
    print(asyncio.run(run_agent(args.task, user=args.user)))

if __name__ == "__main__":
    main()
```

**优点**:零部署成本、易调试、好集成到现有 shell 脚本。
**缺点**:不能多人共享、没有 UI。

##### 2.2 FastAPI / Next.js API

**适合**:Web 产品集成、移动 App 后端、需要鉴权与 multi-tenant 的场景。

**最小实现**:
```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class ChatRequest(BaseModel):
    message: str
    session_id: str | None = None

@app.post("/chat")
async def chat(req: ChatRequest):
    answer = await run_agent(req.message, session_id=req.session_id)
    return {"answer": answer}
```

启动:`uvicorn server:app --host 0.0.0.0 --port 8000 --workers 4`。

**优点**:与现代前端/移动端无缝集成、易扩展。
**缺点**:需要解决长任务、并发、鉴权、限流。

##### 2.3 Slack / Discord / 飞书 Bot

**适合**:团队协作、内部工具、需要"在大家工作的地方"被使用。

**实现思路**:
- 注册 bot,拿到 webhook URL 或 socket-mode token。
- 用 `slack-bolt` / `discord.py` / 飞书 SDK 监听消息。
- 收到 `@bot 帮我整理今天 PR` → 调 Agent → 把结果发回频道。

**优点**:**用户零学习成本**(他们已经在用 Slack);团队协作天然。
**缺点**:平台限速、消息长度上限、多平台维护。

##### 2.4 定时任务(cron / APScheduler / Temporal / Airflow)

**适合**:后台 Agent、日报、巡检、数据同步。

**最简单**(系统 cron):
```cron
0 9 * * * cd /opt/agent && /opt/agent/.venv/bin/python daily.py >> /var/log/agent.log 2>&1
```

**Python 内置调度**:`APScheduler` 跑在自己进程内,适合单机。
**生产级**:Temporal / Airflow,跨机器、可恢复、有 UI。

**优点**:无需用户交互、可靠。
**缺点**:不实时,延迟取决于调度间隔。

##### 2.5 MCP Server + Cursor 等

**适合**:把 Agent 嵌进编码工作流、让其他 AI 产品复用 Agent 能力。

**思路**:把 Agent 本身封装成 MCP Server,提供 `run_agent` 工具,Cursor 调用时把它当成一个超级工具。

> 【讲师讲稿】"选型口诀:**用户在哪里,就把 Agent 放在哪里**。开发者用 CLI;产品用户用 API + 前端;团队用 Bot;后台自动化用 cron。别让用户为你的部署形态改变工作习惯。"

#### 4. 长任务异步化(20 min)

**问题**:Agent 一次跑 30 秒,HTTP 同步接口会:
- LB / Nginx 默认 30~60s 超时,直接断开。
- 单进程阻塞,并发受限(worker 数有限)。
- 客户端体验差(白屏 30 秒)。

**解决:任务异步化 + 状态查询**:

```python
import uuid
from fastapi import BackgroundTasks

TASKS = {}   # 简化版,生产用 Redis

@app.post("/tasks")
def submit(req: ChatRequest, bg: BackgroundTasks):
    task_id = str(uuid.uuid4())
    TASKS[task_id] = {"status": "pending", "answer": None}
    bg.add_task(_run, task_id, req.message)
    return {"task_id": task_id}

async def _run(task_id, message):
    TASKS[task_id]["status"] = "running"
    try:
        ans = await run_agent(message)
        TASKS[task_id] = {"status": "done", "answer": ans}
    except Exception as e:
        TASKS[task_id] = {"status": "failed", "error": str(e)}

@app.get("/tasks/{task_id}")
def get_task(task_id):
    return TASKS.get(task_id, {"status": "not_found"})
```

**更优雅(SSE 流式)**:

```python
from fastapi.responses import StreamingResponse

@app.post("/chat/stream")
async def stream(req: ChatRequest):
    async def events():
        async for chunk in run_agent_streaming(req.message):
            yield f"data: {json.dumps(chunk)}\n\n"
    return StreamingResponse(events(), media_type="text/event-stream")
```

**生产推荐**:**Celery / RQ / Temporal**——把 Agent 任务塞到队列,worker 异步处理,支持重试 / 持久化 / 监控。

> 【讲师讲稿】"长任务异步化是 LLM 应用上线的**必修课**——LLM 调用本身就慢(秒级),Agent 一跑就是几十秒。**任何上线 Agent 都要在异步队列上跑**,这是上线门槛。"

**参考答案**:

```python
# app.py
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field
from typing import Optional
import uvicorn, time, traceback

from my_agent import run_agent, BudgetExceeded     # 复用前面课的 run_agent

app = FastAPI(title="My Agent API", version="0.1.0")

class ChatRequest(BaseModel):
    user_input: str = Field(..., min_length=1, max_length=4000, description="user prompt")
    session_id: Optional[str] = None
    max_steps:  int = Field(10, ge=1, le=20)

class ChatResponse(BaseModel):
    answer:     str
    elapsed_ms: int
    session_id: Optional[str] = None

@app.get("/health")
def health():
    return {"status": "ok"}

@app.post("/chat", response_model=ChatResponse)
def chat(req: ChatRequest):
    t0 = time.time()
    try:
        answer = run_agent(req.user_input, max_steps=req.max_steps)
    except BudgetExceeded as e:
        # 业务异常 → 402 Payment Required(语义最贴)
        raise HTTPException(status_code=402, detail=str(e))
    except Exception as e:
        # 兜底,生产应记日志/告警
        traceback.print_exc()
        raise HTTPException(status_code=500, detail=f"internal: {type(e).__name__}")
    return ChatResponse(
        answer=answer,
        elapsed_ms=int((time.time() - t0) * 1000),
        session_id=req.session_id,
    )

if __name__ == "__main__":
    uvicorn.run("app:app", host="0.0.0.0", port=8000, reload=True)
```

**启动 + 测试**:

```bash
# 启动
uvicorn app:app --reload --port 8000

# 健康检查
curl -s http://localhost:8000/health
# → {"status":"ok"}

# 业务调用
curl -s -X POST http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"user_input": "北京和上海今天天气怎么样?", "max_steps": 5}'
# → {"answer":"北京今天 22°C 多云,上海今天 26°C 雨。","elapsed_ms":2347,"session_id":null}

# 触发预算守卫(假设 MAX_TOTAL_COST=0.01 较低)
curl -i -X POST http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"user_input": "反复调 50 次 get_weather"}'
# → HTTP/1.1 402 Payment Required
# → {"detail":"total $0.0234 exceeded budget $0.01, ..."}

# 测试输入校验(空字符串应被 Pydantic 挡掉)
curl -i -X POST http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"user_input": ""}'
# → HTTP/1.1 422 Unprocessable Entity   (Pydantic min_length=1 触发)
```

**评分要点**:
1. 用 **Pydantic** 声明请求/响应模型(`min_length` / `max_length` / `ge` / `le` 等约束),不能裸 dict;
2. **每个业务异常用不同 HTTP code**(预算→402,鉴权→401,参数→400,内部→500),不要一律 500;
3. 有 `/health` endpoint(K8s liveness probe 必需,M7 L33 已示范);
4. 有 `elapsed_ms` 在响应里(便于客户端 SLA 监控,且产品端 UI 可显示);
5. **下一步改造方向**(L34 内容):chat 改 async + 加 request_id 链路追踪 + 长任务改 202 + polling。

#### 练习 1:FastAPI 同步端点(15 min,个人)

**任务**:实现 `POST /chat` 端点,把 hello-agent 的 `run(query)` 包成同步 API。

**骨架代码 `main.py`**:
```python
import os
from fastapi import FastAPI, HTTPException, Header, Depends
from pydantic import BaseModel, Field
from agent import run_agent            # M2 hello-agent 的核心函数,返 {"answer":..., "cost":..., "steps":...}

app = FastAPI(title="Hello Agent API", version="1.0")

class ChatIn(BaseModel):
    user_input: str = Field(..., min_length=1, max_length=2000)
    session_id: str | None = None
    user_id: str = "anonymous"

class ChatOut(BaseModel):
    answer: str
    cost_usd: float
    steps: int
    session_id: str

def verify_api_key(x_api_key: str = Header(...)):
    if x_api_key != os.getenv("SERVICE_API_KEY", "dev-key"):
        raise HTTPException(401, "invalid api key")
    return x_api_key

@app.get("/health")
def health():
    return {"status":"ok"}

@app.post("/chat", response_model=ChatOut)
def chat_sync(body: ChatIn, _=Depends(verify_api_key)):
    try:
        result = run_agent(body.user_input, session_id=body.session_id, user_id=body.user_id)
    except Exception as e:
        raise HTTPException(500, f"agent error: {e}")
    return ChatOut(
        answer=result["answer"],
        cost_usd=result["cost"],
        steps=result["steps"],
        session_id=result.get("session_id", body.session_id or "new"),
    )
```

```bash

```

#### 练习 2:异步任务 + 状态查询(20 min,个人)

**任务**:实现 `POST /chat/async` + `GET /chat/{task_id}`,支持"长任务不阻塞"模式。

**骨架**:
```python
from fastapi import BackgroundTasks
from uuid import uuid4

TASKS: dict[str, dict] = {}                       # 教学用内存 dict;生产用 Redis

def _do_and_store(task_id: str, body: ChatIn):
    """后台跑 agent,把结果存 TASKS"""
    try:
        result = run_agent(body.user_input, session_id=body.session_id, user_id=body.user_id)
        TASKS[task_id] = {"status":"done", "result":result}
    except Exception as e:
        TASKS[task_id] = {"status":"failed", "error":str(e)}

@app.post("/chat/async")
def chat_async(body: ChatIn, bg: BackgroundTasks, _=Depends(verify_api_key)):
    task_id = uuid4().hex
    TASKS[task_id] = {"status":"running", "submitted_at":str(datetime.utcnow())}
    bg.add_task(_do_and_store, task_id, body)
    return {"task_id": task_id, "status":"submitted"}

@app.get("/chat/{task_id}")
def get_task(task_id: str, _=Depends(verify_api_key)):
    if task_id not in TASKS:
```

##### 3.3 签名校验

GitHub 每次 webhook 请求,会带一个 header `X-Hub-Signature-256: sha256=<hash>`,这是用 secret + body 计算出来的 HMAC。**必须校验**,否则任何人都能伪造请求。

```python
import hmac, hashlib

WEBHOOK_SECRET = os.environ["GITHUB_WEBHOOK_SECRET"]

def verify(body: bytes, signature: str) -> bool:
    if not signature or not signature.startswith("sha256="):
        return False
    expected = "sha256=" + hmac.new(
        WEBHOOK_SECRET.encode(), body, hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(expected, signature)
```

**用 `hmac.compare_digest`**——不是 `==`!`==` 在某些 Python 实现里是**短路比较**,可能被时序攻击。这是网络安全工程的小常识。

##### 3.4 幂等(去重)

Webhook **会重复投递**——网络抖动、GitHub 重试机制、你这边 5xx 等都会触发。

每个 webhook 事件都带一个唯一 ID(`X-GitHub-Delivery`)。**用它做去重**:

```python
import redis
r = redis.Redis(...)

@app.post("/webhook/github")
async def github_hook(request: Request):
    body = await request.body()
    sig = request.headers.get("X-Hub-Signature-256")
    if not verify(body, sig):
        return {"ok": False, "reason": "invalid signature"}
    
    delivery = request.headers.get("X-GitHub-Delivery")
    # SETNX:仅当 key 不存在时设置,返回 True;已存在返回 False
    if not r.set(f"gh_delivered:{delivery}", "1", nx=True, ex=86400):
        return {"ok": True, "reason": "duplicate, skipped"}
    
    payload = json.loads(body)
    if payload.get("action") == "opened" and "issue" in payload:
        # 异步处理,不阻塞 webhook 响应
        asyncio.create_task(handle_new_issue(payload))
    
    return {"ok": True}
```

**关键**:
- `r.set(key, value, nx=True, ex=86400)` 是 Redis 原子操作,**多副本部署也安全**。
- TTL 86400(1 天)是经验值——GitHub 不会重投 24h 之前的事件。
- **响应要快**(<10s),否则 GitHub 会重发。复杂处理放到 `asyncio.create_task` 异步跑。

#### 4. 失败兜底:Webhook + cron 双保险(15 min)

> 【讲师讲稿】"再强的 Webhook 也会**偶尔丢事件**——你的服务宕机 1 小时、网络分区、GitHub 自己 bug。所以生产 Agent 通常用**'Webhook + 低频 cron 兜底'** 的双保险:webhook 负责实时,cron 每小时扫一次最近 1 小时的事件,把漏掉的补上(基于已处理 ID 集合去重)。"

```python
@sched.scheduled_job("interval", minutes=60)
def reconcile():
    """每小时同步过去 1 小时的 issue,补 webhook 漏的"""
    recent = github.list_issues(since=datetime.now() - timedelta(hours=1))
    for issue in recent:
        delivery = f"reconcile_{issue.id}_{issue.updated_at}"
        if r.set(f"gh_delivered:{delivery}", "1", nx=True, ex=86400):
            asyncio.create_task(handle_new_issue({"action":"opened","issue":issue}))
```

加上**投递成功率监控**:每天看 `gh_delivered:*` key 数和实际 issue 数对比,如果差距 >5% 就告警。

```python
import hmac, hashlib, os, asyncio

from agent import run_agent

app = FastAPI()
SECRET = os.environ["GH_WEBHOOK_SECRET"].encode()
SEEN = set()                      # 教学用内存 dedup;生产用 Redis with TTL

@app.post("/gh")

    body = await request.body()

    # 1. 签名校验
    if not x_hub_signature_256:
        raise HTTPException(401, "missing signature")
    expected = "sha256=" + hmac.new(SECRET, body, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expected, x_hub_signature_256):
        raise HTTPException(401, "bad signature")

    # 2. 幂等去重
    if x_github_delivery in SEEN:
        return {"ok": True, "dedup": True}
    SEEN.add(x_github_delivery)

    # 3. 立即 200,异步 fire-and-forget(GitHub 要求 10s 内响应)
    payload = await request.json()
    asyncio.create_task(_process(x_github_event, payload))
    return {"ok": True, "event": x_github_event}

async def _process(event: str, payload: dict):
    """异步处理 Agent 任务"""
    if event == "issues" and payload.get("action") == "opened":
        title = payload["issue"]["title"]
        body = payload["issue"]["body"] or ""
        print(f"[webhook] new issue: {title}")
        # 用 Agent 分析 issue,写建议 comment(此处 mock)
        result = run_agent(f"分析这个 GitHub issue 并写 3 行 review comment:{title}\n{body}",
                           user_id="github-bot")
        print(f"[webhook] agent reply:\n{result['answer']}")

if __name__ == "__main__":
    import uvicorn
    uvicorn.run(app, host="0.0.0.0", port=8000)
```

### 八、测查题与参考答案

1. 事件触发场景对实时性要求很高(秒级响应),应选?  A. 高频轮询  **B. Webhook 推送(对方有事件主动推到你的 endpoint,秒级、零无效请求)**  C. 每分钟 cron  D. 手动触发 → **B**。Webhook 是"事件驱动"的标准方案;轮询是无奈替代,代价是延迟 + 大量空请求。
2. cron 表达式 `0 9 * * *` 表示?  A. 每 9 分钟一次  **B. 每天 9:00 整执行一次(`分 时 日 月 星期`)**  C. 9 月 0 日  D. 周日 9:00 → **B**。cron 5 字段是"分 时 日 月 星期",* 表示通配;调试可用 [crontab.guru](https://crontab.guru) 验证。
3. 接收 Webhook **必须**做的安全措施是?  **A. HTTPS(防中间人篡改)+ 签名校验(用对方 secret 验证 payload 是真发件人发的,而非伪造)**  B. 仅打开 80 端口  C. 不需要,内网就行  D. 用 GET 接收 → **A**。GitHub / Stripe 等都用 HMAC-SHA256 签名;不验签等于谁都能伪造事件让你的 Agent 干活/转账。
4. **简答**:Webhook 重复投递怎么办?
   - **参考答案**:幂等设计——用事件 ID(`X-GitHub-Delivery` 等)做去重表 / Redis SETNX,同事件多次到达只处理一次;响应快速,失败让对方重试。
5. **场景**:GitHub Webhook 偶尔丢失,怎么兜底?
   - **参考答案**:① 加低频 cron 同步过去 1 小时 issue;② 用已处理 ID 集合补漏(同一 ID 不重复处理);③ 监控投递成功率,差距 >5% 告警;④ 重要事件用多通道(Webhook + 日志拉取)双写。

##### 2.1 Prompt 前缀缓存

OpenAI 和 Anthropic 都支持**自动 prompt 缓存**——当 system + 早期 messages **完全相同**且**间隔较短**(几分钟内),后续请求的这部分**只收 25~50% 价格**。

**触发条件**:
- 前缀 >= 1024 tokens(OpenAI)。
- 前缀完全相同(包括标点)。
- 间隔 < 5~10 分钟。

**优化技巧**:
- **system 写稳定**——不要在 system 里塞动态字段(如当前时间、用户名),那样每次前缀都不同,无法缓存。
- **把动态信息放 user 末尾**:`{static_system} + {static_few_shot} + {dynamic_user}`。

##### 2.2 滚动窗口 + 摘要

L19 已详讲。**把每轮 messages 从 6000 token 压到 2000 token,直接砍 60% 输入成本**。

##### 2.3 模型分级

**核心思想**:简单步用小/便宜模型,关键步用大/贵模型。

```python
def llm(messages, complexity="auto", tools=None):
    if complexity == "high" or _needs_strong(messages):
        model = "gpt-4.1"     # 贵
    else:
        model = "gpt-4.1-mini"   # 便宜
    return client.chat.completions.create(model=model, messages=messages, tools=tools)
```

**怎么判断 complexity**:
- 启发式:消息数 > N 用大模型;首次决策用大模型,工具结果汇总用小模型。
- LLM-as-Router:第一轮用 mini 模型先判断"这任务需要什么档位的模型"。

**风险**:小模型在关键步出错 → 后续连锁错误 → **总成本反升**。

> 【讲师讲稿】"模型分级**必须配合 eval**——你要有数据证明'某些步降级后,success rate 没下降'。**没 eval 不要做分级**,否则你只是在赌博,赌输了一片乱。"

##### 2.4 工具结果裁剪

工具返回 1MB JSON?**先在工具内部摘要**:

```python

def search_kb(query: str, k: int = 5) -> str:
    results = vector_db.query(query, k=k)

                  for r in results]

```

或者:**返回 reference ID**,LLM 需要详情时再调 `get_detail(id)`。

##### 2.5 并行工具调用

L10 已讲。把串行 N×1s 改成并行 max(1s),**延迟降 N 倍**,token 不变。

##### 2.6 流式输出

```python
stream = client.chat.completions.create(model=..., messages=..., stream=True)
for chunk in stream:
    delta = chunk.choices[0].delta.content
    if delta: print(delta, end="", flush=True)
```

**不省钱**,但**用户感觉快很多**——首 token 在 1 秒内出现,而不是等 10 秒看完整回复。**体感速度对产品成败影响巨大**。

##### 2.7 向量缓存

```python
def cached_run_agent(query):
    embedding = embed(query)
    hit = cache_db.query(embedding, k=1, threshold=0.95)
    if hit:
        return hit["answer"]   # 直接返回,零 LLM 调用
    answer = run_agent(query)
    cache_db.add(embedding, answer)
    return answer
```

**适合**:FAQ 类、查询类高度重复的场景。**不适合**:需要实时数据的任务(天气、库存)。

**优化 B:answer 缓存**(相同 query 5 min 内不重跑)

```python
import hashlib, time
_CACHE: dict[str, tuple[float, dict]] = {}
CACHE_TTL = 300     # 5 min

def _cache_key(user_input: str, user_id: str) -> str:
    return hashlib.sha256(f"{user_id}::{user_input}".encode()).hexdigest()

def cached_run(user_input: str, user_id: str):
    key = _cache_key(user_input, user_id)
    now = time.time()
    if key in _CACHE:
        ts, result = _CACHE[key]
        if now - ts < CACHE_TTL:
            print(f"[cache HIT] {user_input[:30]}")
            return result
    result = run_agent(user_input, user_id=user_id)
    _CACHE[key] = (now, result)
    return result
```

```python
        model="gpt-4o-mini",
        messages=[
            {"role":"system","content":"用 3 句话总结下面工具返回的内容(保留数字和关键实体):"},
            {"role":"user","content":result[:8000]},
        ],
    )
    return f"[Summarized from {len(result)} chars]:\n{summary_resp.choices[0].message.content}"

# 主循环里
for call in msg.tool_calls:
    raw = REGISTRY[call.function.name](**args)
    trimmed = maybe_summarize_tool_result(call.function.name, str(raw))
    messages.append({"role":"tool","tool_call_id":call.id,"content":trimmed})
```

**验收 checklist**:
- [ ] 3 类优化都实现且能跑
- [ ] A 优化在"1+1"这种 query 上选到 gpt-4o-mini(不用 gpt-4.1)
- [ ] B 优化重复 query 命中缓存,打印 `[cache HIT]`
- [ ] C 优化用 tool 返回上万字文本(如假 wiki),观察被摘要到 ≤ 500 字塞回

#### 练习 3:A/B 对比 baseline vs 优化后(20 min,个人)

**任务**:同 30 条 eval 集,跑 baseline vs 优化版,记录对比。

**benchmark 脚本 `benchmark.py`**:
```python
import time, json

def benchmark(version_name: str, agent_fn, eval_path="eval_seed.jsonl"):
    items = [json.loads(l) for l in open(eval_path,encoding="utf-8")]
    total_time = 0
    total_cost = 0
    total_tokens = 0
    pass_count = 0
    for it in items:
        t0 = time.perf_counter()
        r = agent_fn(it["user"])
        total_time += (time.perf_counter() - t0)
        total_cost += r.get("cost", 0)
        total_tokens += r.get("tokens", 0)
        # 简易 pass 判断(用 M6 L31 rule_score)
        if _check_pass(it, r):
            pass_count += 1
    n = len(items)
    print(f"\n=== {version_name} ===")
    print(f"  pass_rate = {pass_count/n:.1%}")
    print(f"  avg_time = {total_time/n:.2f}s")
    print(f"  avg_cost = ${total_cost/n:.4f}")
    print(f"  avg_tokens = {total_tokens/n:.0f}")

benchmark("baseline", run_agent)
benchmark("optimized", cached_run_with_tier)
```

**对比表**(填自己数据):

| 版本 | pass_rate | avg time | avg cost | avg tokens |
| ---- | ---- | ---- | ---- | ---- |
| baseline | | | | |
| +模型分级(A) | | | | |
| +缓存(A+B) | | | | |

**期望降幅**(参考):
- avg_time:-40% 到 -60%
- avg_cost:-50% 到 -70%
- avg_tokens:-40% 到 -60%
- pass_rate:**不应下降**;若下降 > 3% 说明优化太激进(如缓存 TTL 太长)

**验收 checklist**:
- [ ] 4 个版本都跑完 30 条,数据填入表格
- [ ] pass_rate 未显著下降(≤ 3% 波动)
- [ ] cost 或 tokens 明显下降(至少 -30%)
- [ ] 有一版本因优化过激而分数下降,能定位原因

**常见坑**:
- 优化只看 cost 不看 pass_rate → 便宜但答非所问
- cache TTL 设得太长(如 1 天)→ 用户明显感受到"我刚问过,答案已经过时了"
- 模型分级判断规则太粗(如只按长度)→ 长 query 也可能是简单的,反之亦然
- 忘了在优化后**跑 eval**(M6 L31)兜底 → 没有 eval 的优化就是拍脑袋

**挑战延伸(选做)**:
- 加**流式**优化:让 UI 更快看到第一 token(TTFT 从 2s 降到 0.3s),用户感知飞升
- 加 **prompt caching**(OpenAI/Anthropic 都支持):cached input tokens 通常 1 折
- 加 **vector cache**(不精确匹配也能命中近似问题):用 embedding 相似度 > 0.95 时复用

### 八、测查题与参考答案

1. 下面哪个**不是**有效的降本手段?  A. 开启 prompt 前缀缓存(cached input 单价显著低)  B. 简单步骤切换到 mini 模型(模型分级)  **C. 调高 temperature 让模型多采样几次(反而成本上升、质量更不稳定)**  D. 长 tool 结果先摘要再回填 → **C**。temperature 与采样次数本质上都是"花更多钱换多样性",在降本场景反过来用。
2. 流式输出(streaming)主要改善的是?  A. 总 token 数  **B. 用户感知速度——首 token 延迟从几秒压到几百毫秒,体感"立刻有反馈"**  C. 模型推理质量  D. 调用次数 → **B**。流式不省钱也不改质量,但显著改善 UX,是聊天/写作类 Agent 上线必备。
3. Agent 成本热点(token 消耗大头)**通常**出在?  **A. 长 system prompt 每轮重复传 + 长 tool 调用结果反复拼回 messages**  B. SDK 自身开销  C. 调用次数太少  D. JSON 解析 → **A**。这两类是"看不见的怪兽",前缀缓存能解第一类,工具结果摘要 / 引用号能解第二类。
4. **简答**:为什么模型分级要谨慎?
   - **参考答案**:小模型在关键步出错→连锁错误→总成本反升;必须配合 eval 决定哪些步可降级,并保留 fallback 机制(降级失败回退到大模型)。
5. **场景**:3 万 tokens / $0.1 → 目标 $0.03,4 个动作?
   - **参考答案**:① 开启 prompt 前缀缓存(让 system 稳定);② 滚动 + 摘要降到 1 万 token;③ 简单步切 mini 模型;④ 工具结果摘要回填;⑤ 向量缓存复用相似 query;⑥ 并行工具降总耗时。

### 九、教学反思要点
- 学员是否拿出真实 trace 来分析?如果没有,可以用讲师的样本数据。
- 优化后用 eval 验证质量不下降,这是模块 6+7 的闭环。
